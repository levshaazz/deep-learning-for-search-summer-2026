RAG-ретриверны җый, аннары аны хөкем ит

Корпоратив корпусны чанклап, «recall floor»’ны үлчә; multi-query, HyDE һәм RAG-Fusion белән ретривны күтәр; аннары аны кулдан бәялә (gold answer-facts’тан context precision һәм recall) һәм LLM-хөкемченең позиция, күп сүзлелек һәм Гудхарт смещениеләрен ач — өстәп бер мәкалә эссесе.

Тәрҗемә бара — кайбер текст хәзергә башка телдә күрсәтелә.

Строится на setup EnterpriseRAG-Bench из Лабы 3 — ты переиспользуешь КОД BM25 из Лабы 1 и dense-ретривера из Лабы 2, переиндексировав его на этом корпусе (не ANN-индекс из Лабы 3; точный поиск на этом масштабе нормален). Часть 1 строит retrieval-половину RAG-системы на реальном корпоративном корпусе и учится ей не доверять слепо; часть 2 — внимательное чтение одной статьи с рукописной переинтерпретацией её hero-фигуры. Центральная рамка — recall floor: если ответа нет в извлечённом контексте, никакой генератор его не вернёт — значит, ретривер и его оценка и есть место, где выигрывается или проигрывается качество.

Мәгълүмат җыелмасы һәм setup

Используй EnterpriseRAG-Bench на фиксированной подвыборке ≥200 вопросов (укажи какой; напр. первые 200 по question_id). Каждый вопрос несёт expected_doc_ids (ground-truth документы — релевантность здесь БИНАРНАЯ, поэтому nDCG на gains 0/1, а любой неизвлечённый документ считается rel 0), gold_answer и answer_facts (список атомарных фактов, которые ответ обязан содержать) — именно answer_facts делают context recall вычислимым руками без полного генератора. СТРИМь корпус ~500К документов и держи подвыборку под ноутбук = срезы source_type, на которые ссылаются твои вопросы (сэмпл seed-20260605, если велик), ОБЪЕДИНИ со всеми expected_doc_id оцениваемых вопросов, чтобы ни один gold-документ не выпал (выпавший gold тихо занижает recall). Переиспользуй КОД BM25 из Лабы 1 и dense-ретривера из Лабы 2, переиндексировав на этом корпусе. Единица ретрива: ранжируешь ЧАНКИ; чанк релевантен ⇔ его родительский doc_id ∈ expected_doc_ids. Режь каждый результат по question_type (значения в нижнем регистре, напр. "basic", "conflicting_info", "info_not_found", …) — категории и есть смысл этого бенчмарка.

Часть 1 — Код и эксперименты (60%)

  1. Исследование чанкования (руками, чистые строки): реализуй fixed-size и recursive (абзац → предложение → слово) чанкование, размеры/overlap в токенах. На длинных корпоративных документах перебери размер чанка × overlap и меряй recall как answer-fact containment — «присутствует» ли gold-факт в каком-то чанке его expected_doc? Зафиксируй ОДНО правило сопоставления и используй везде: факт присутствует в чанке ⇔ cosine(факт, чанк) ≥ 0.6 под твоим энкодером из Лабы 2 (укажи порог; факт редко встречается дословно, так что точное строковое совпадение — слишком строгий критерий). Это эвристический прокси, не семантическая истина. Дай формулу числа чанков: n = 0 при L=0, иначе max(1, ⌈(L−overlap)/(size−overlap)⌉); параметры целые, L≥0 и 0≤overlap<size, покажи факт, разорванный границей чанка при overlap 0 (present 0), который спасает малый overlap (present 1), и отчитайся о прокси-покрытии фактов: доле answer_facts, прошедших правило сопоставления. Это НЕ нижняя и не верхняя граница качества генератора: близость не доказывает логического следования, а факт может собираться из нескольких чанков. Вручную проверь выборку, включая отрицания и разорванные факты, и обсуди ложные совпадения и пропуски.
  2. Переписывание запроса (lift ретрива): реализуй три техники, которые правят запрос и не трогают ретривер — multi-query (найти несколько парафраз, затем слить в ОДНО ранжирование, оценивая каждый документ ЛУЧШЕЙ (max) близостью, которую он получил среди прогонов парафраз, чтобы MRR/nDCG были определены — голое объединение множеств — ещё не ранжирование), HyDE (закодировать гипотетический ответ и искать рядом) и RAG-Fusion (слить прогоны парафраз через RRF, k=60, руками). Сгенерируй парафразы/гипотезы маленьким локальным генератором или напиши фиксированный набор руками и закоммить в репозиторий для воспроизводимости. Меряй прирост recall@k, MRR и nDCG над обычным запросом и объясни каждый результат через vocabulary gap между коротким вопросом и длинным жаргонным корпоративным документом.
  3. Оценка RAG руками (без библиотеки RAGAS): context precision = среднее AP по запросам (знаменатель AP — ВСЕ релевантные родительские документы из разметки), но СНАЧАЛА сдедупь чанки до родительского документа (сверни ранжирование чанков к первому встреченному рангу каждого различного doc_id, затем усредни precision@k на рангах релевантных документов) — иначе несколько почти-дубликатов чанков одного gold-документа прижимают precision к 1 и метрика плывёт с размером чанка. Прокси context recall = (# gold answer_facts, сопоставленных хотя бы с одним извлечённым чанком) / (# answer_facts), с ТЕМ ЖЕ правилом сопоставления cosine ≥ 0.6, что и в чанковании — без генератора. Дай оба по question_type. Для категории info_not_found метрики N/A (нет релевантных документов, пустые answer_facts → 0/0): вместо этого дай метрику ABSTENTION — долю таких вопросов, у которых близость top-1 чанка ниже заявленного порога τ (правильное «ничего уверенно не выдавать») — и сравни с контрольной категорией.
  4. Лаборатория смещений LLM-судьи: тут нужен маленький замороженный локальный судья (~8B instruct, temperature 0, фикс seed) — смещения position и verbosity это эмпирические доли, которые выдаёт судья, «руками» их не получить. Сначала собери ~15–20 ПАР ответов из данных: для нескольких вопросов возьми gold_answer как ответ A и построй B двумя способами — (i) парафраз A (честная ничья, для position) и (ii) A, раздутый релевантным «наполнителем» без новых фактов (то же содержание, длиннее, для verbosity). Дай судье фиксированную рубрику 1–5 (relevance, grounding, completeness). Измерь: position — гоняй каждую ничью в ОБОИХ порядках A/B, дай долю следования позиции; verbosity — дай, как часто побеждает более длинный ответ. Затем ЧИСТО РУКАМИ (без модели) воспроизведи Goodhart-флип весов: честный A = mean[5,5,3] = 4.3333 бьёт раздутый C = mean[4,3,5] = 4.0, но удвой вес completeness — и C = (4+3+2·5)/4 = 4.25 выигрывает без единого изменённого слова — веса рубрики и есть поверхность атаки. Наконец реализуй swap-and-average (победа засчитывается, только если один ответ выиграл в обоих порядках) и перемеряй долю position; дай снижение.
  5. Метрики и значимость: для лучшего переписывания против BM25-бейзлайна прогони парный тест (t-test и/или Wilcoxon) по per-query context precision — средняя разница, 95% CI, p-value и честная интерпретация (необходимо-но-недостаточно; поправка на множественные сравнения, когда перебираешь много конфигов).
  6. Отчёт: графики + таблицы + обсуждение, связывающее прокси-покрытие фактов, прирост от переписывания, RAG-метрики руками и находки о смещениях судьи в одну историю — где реально выигрывается качество в RAG-пайплайне и почему нельзя жёстко оптимизировать под неаудированного судью.

Автогрейдер Stepik — контрольные числа

RAG-логику «руками» проверяет детерминированный автогрейдер (stepik/graders/grader_a3_rag.py): мини-мемо из 52 токенов с gold answer-facts, замороженное ранжирование чанков и два замороженных списка вердиктов судьи вшиты в чекер. Одна замена: правило сопоставления cosine >= 0.6 из полной домашки на раннере заменено правилом пересечения токенов (>= 0.8 множества токенов факта) — энкодера на раннере нет. Допуск 1e-4; исследование на EnterpriseRAG-Bench и живые доли смещений LLM-судьи идут в отчёт (peer-review).

# solution.py — обязательные функции (Stepik: grader_a3_rag.py)
n_chunks(L, size, overlap)                # 0 if L=0; else max(1, ceil((L-overlap)/(size-overlap)))
chunk_fixed(tokens, size, overlap)        # окна с шагом size-overlap
fact_present(fact, chunk)                 # пересечение токенов >= 0.8
recall_floor(facts, chunks) · context_recall(facts, chunks)
context_precision(parents, relevant)      # dedup до документа, потом AP
weighted_mean(scores, weights)
position_follow_rate(run1, run2) · consistent_win_rate(run1, run2)

# Контрольные числа (мини-мемо 52 токена + замороженные вердикты):
n_chunks(1000, 200, 50) = 7
recall floor (size=16): overlap=0 -> 0.50 · overlap=4 -> 0.75   # overlap спасает факт
context_precision([d1,d1,d2,d3,d1,d4], {d1,d3}) = 0.8333        # dedup-MAP

            -> A=4.0000 < C=4.2500 (completeness x2, ни слова не изменено)
position_follow_rate = 0.5000 · consistent_win_rate (swap-and-average) = 0.3333

Часть 2 — Чтение статьи и рукописное эссе (40%)

Выбери одну из статей ниже, внимательно прочитай и напиши рукописное эссе на две страницы A4 своими словами — твоя интерпретация, не пересказ. Затем выполни подзадачу с hero-фигурой.

Подзадача: hero-фигура. Определи hero-фигуру статьи — диаграмму, несущую её центральную идею. Перерисуй её по-своему (можно от руки), чтобы раскрыть концепт глубже оригинала: смени кодировку, добавь недостающую ось/подпись, покажи случай отказа или перерисуй на своих числах из домашки (твоя кривая recall floor, твой прирост от переписывания, твои доли смещений судьи). Добавь короткую подпись — что твой вариант делает видимым, чего не было в оригинале.
