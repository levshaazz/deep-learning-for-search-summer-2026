## Spine position
The **border crossing of the whole course.** Territories I–III answered *Get Data → Measure → Rank*; for ten
lectures the Ship's job has been to **find and order** records. **L15 adds a fourth leg — *Generate* — on top of
Rank:** retrieval-augmented generation feeds the ranked passages into a language model so the Ship **answers in
words**, not just returns a list. The Ship part it builds is the **Oracle**: the retrieve → augment → generate
loop, the **chunking** that decides what can be retrieved at all, and the **query understanding/rewriting** that
aims the retriever at what the captain *really* asked. It is cumulative — the index (L3), the embeddings (L5/L6),
the cascade (L7/L8), and the **ANN lanes (L13)** are all *upstream* of the Oracle now; RAG does not replace
retrieval, it **consumes** it. The hook is the failure of a bare LLM (confident, ungrounded, stale) — grounding it
in *our* retrieval is the mission. Because this is the spine's first new leg in ten lectures, **the spine map gains a
fourth stop — *Generate* — for good** (owner-locked): the spine slide animates *Rank → Generate*, and L11/L12 inherit
the new stop.

**The load-bearing figure of L15 is the RAG pipeline itself.** Per NARRATIVE_METHOD P3 (one governing spatial
metaphor) + P5/P11 (the figure *is* the argument, and the spine question recurs), the `rag-pipeline` widget —
`chunk → embed → retrieve → stuff → generate` — is the **anatomy of the Oracle** and **recurs as the lecture's anchor**
(like the course spine slide, and like L10's reuse of `retrieve-rank-funnel`): the master blueprint is built on
`climb-rag`, then the *same* figure returns with **one stage in focus** on each later beat — the **chunk→embed** stage
on the chunking turn, the **query→retrieve** stage on the rewrite turn, a **poisoned retrieve→stuff** on the catch, and
the **whole pipe lit green** on the payoff. One running example (`data/l10-rag.json`) threads the entire lecture, the
way L5's 8-doc set and L10's cascade-nDCG set did.

## Per climb — worked toy examples, numbers, data schema, generator, gating
> **Lesson honored (L12):** worked arithmetic slides are **`data-type="formula"`** (the 280% formula-stage), pipeline
> blueprints are `archflow`, traces are `e2e`/`walkthrough`.
> **Coverage-guard mechanics (get this right):** the signature is `\d+\.\d{2,}` — it matches a decimal with **≥2
> fractional digits**. So decimals with ≥2 places (RR **0.125**; and L13's distances **0.7071** etc.) **are** caught and
> **MUST** be gated `[C]`. But **single-decimal recalls/RRs (0.5, 0.8, 1.0, 0.4, 0.0) are NOT caught** — the guard
> sees no ≥2-digit decimal, so they slip through silently; each needs an **explicit [C]-claim** OR a two-decimal
> render (`0.50` / `0.80` / `1.00` / `0.40`). Integers (4096, 256, 200, 5, 7, rank 8/2) are likewise un-caught and
> still get `[C]` claims for drift safety. *(The earlier draft's "0.5/0.8 MUST be gated or they HARD-fail the guard"
> was mechanically wrong — the guard never sees them.)*

### Climb 1 — `climb-rag` (retrieve → stuff → generate + token budget) · deck `archflow` + `formula` · REUSE `rag-pipeline`
- **Toy (exact):** context window **4096** tokens. System prompt **200** + query **30** + **k** chunks × **256**
  tokens each, reserving **512** tokens for the answer. Stuffed at k=4 → **1024** tokens; total prompt **1254**;
  headroom **2842**. Max chunks: **k_max = floor((4096 − 200 − 30 − 512) / 256) = floor(3354/256) = 13.** So **k ≤ 13**
  — the context window *caps* how much you can retrieve, which is exactly *why* chunking and ranking matter.
- **Numbers:** stuffed@k4 = 1024 tok; prompt = 1254; headroom = 2842; **k_max = 13**.
- **`data/l10-rag.json` schema (the lecture's anchor trace — richest file):** `{contextWindow:4096, systemTokens:200,
  queryTokens:30, answerReserve:512, chunkTokens:256, stages:["chunk","embed","retrieve","stuff","generate"],
  worked:{k:4, stuffed, promptTotal, headroom}, kMax, trace:{query, retrieved:[{id,score,chunk}…], prompt, answer}}`.
  The same `chunk`/`retrieve` fields are **re-used by `climb-chunking` and `climb-queryrewrite`** (one running example
  for the whole lecture), and `stages` drives the `focusStage` recurrences on the chunking/rewrite/catch/payoff beats.
- **Generator:** `_research/gen_l10.py` (stdlib): integer token arithmetic; `kMax = (ctx − sys − q − reserve)//chunk`.
- **Gating:** token integers are coverage-exempt but `[C]`-claimed (kMax=13, stuffed=1024); `provenance_l10` pins
  `kMax == (contextWindow − systemTokens − queryTokens − answerReserve)//chunkTokens`. The retrieved-doc *scores* (if
  displayed with ≥2-dp) are coverage-caught and gated. *(Exhaustive-gating rule: at build, **every** displayed ≥2-dp
  intermediate on the slide and in the Book — every score/recall/RR, not just the headline numbers listed here — gets a
  `[C]`-claim, modeled on the exhaustive `l8_deck_claims()`; the data file must expose each displayed intermediate as a
  claimable field.)*
- **Anchor role:** `climb-rag` builds the **master pipeline figure**; the *same* `rag-pipeline` widget then recurs
  with `focusStage` on beats 4/6/8/9 (chunk→embed · query→retrieve · poisoned retrieve→stuff · all-green). It is a
  *figure*, not a creature, so its recurrence on turn/catch/payoff beats is P9-clean; the two climbs that follow

### Climb 2 — `climb-chunking` (size/overlap → retrieval quality) · deck `walkthrough` + `formula` · NEW `chunking-demo`
- **Toy (exact):** document **L=1000** tokens; the answer span sits at tokens **[380, 470]** (90 tokens).
  - **size=200, overlap=0:** n_chunks = ceil((1000−0)/(200−0)) = **5**; windows [0,200],[200,400],[400,600]… → the
    answer **straddles boundary 400** (20 tokens in chunk 2, 70 in chunk 3) → no single chunk holds the full span →
    **recall@3 = 0** (binary **answer-containment**: the one relevant unit is the gold answer span [380,470], and no
    retrieved chunk contains it whole — the span is fragmented across chunks 2 and 3).
  - **size=200, overlap=50:** n_chunks = ceil((1000−50)/(200−50)) = ceil(6.33) = **7**; window **[300,500]** fully
    contains [380,470] → **recall@3 = 1.0** (binary containment satisfied).
- **Numbers:** 5 → 7 chunks (more storage); recall@3 **0 → 1.0** (binary answer-containment — *one* answer span, so
  recall is 0/1, not fractional); the straddle (chunk 2/3 split 20/70).
- **`data/l10-chunking.json` schema:** `{docLen:1000, answerSpan:[380,470], scenarios:[{size,overlap,nChunks,
  windows:[[s,e]…], answerChunk:idx|null, recallAt3∈{0,1}}…], formula:"ceil((L−o)/(size−o))"}`. `recallAt3` is the
  **binary answer-containment** (`1` iff some window fully contains `answerSpan`, else `0`); `answerChunk` is that
  window's index or `null`.
- **Generator:** `gen_l10.py` (stdlib): `nChunks = ceil((L−o)/(size−o))`; `recallAt3 = 1` iff some scenario window
  fully contains `answerSpan`, else `0` (binary containment — the displayed recall *is* this value, recomputed, not a
  partial/fractional score).
- **Gating:** `[C]` on **1.0** — a **single-decimal** value, so it is **NOT** caught by the coverage-guard's
  `\d+\.\d{2,}` signature and needs an **explicit [C]-claim** (or a `1.00` render); nChunks integers coverage-exempt
  but `[C]`-claimed; `provenance_l10` recomputes `nChunks` from L/size/overlap and the **binary answer-containment**
  (recall ∈ {0,1}) from the windows + the committed `answerSpan`. *(Exhaustive-gating rule: at build, **every**
  displayed ≥2-dp intermediate on the slide and in the Book — not just the headline numbers listed here — gets a
  `[C]`-claim, modeled on the exhaustive `l8_deck_claims()`; the data file must expose each displayed intermediate as a
  claimable field.)*

### Climb 3 — `climb-queryrewrite` (HyDE / multi-query → recall lift) · deck `e2e` + `formula` · NEW `query-rewrite`
- **Toy (exact):** query *"How does the heart pump blood?"* (short, vocabulary-poor). The true doc uses *"cardiac
  cycle / ventricular contraction / systole"* → lexical+dense mismatch → true doc retrieved at **rank 8** →
  **recall@5 = 0**, **RR = 1/8 = 0.125**.
  - **HyDE:** an LLM writes a hypothetical answer paragraph (rich with *cardiac cycle, ventricles, systole*); embed
    *that* → its vector lands near the true doc → true doc rises to **rank 2** → **recall@5 = 1**, **RR = 1/2 = 0.5**.
    *(HyDE is scored on the **single-true-doc** model, so its recall@5 is **binary** 0→1.)*
  - **Multi-query:** evaluated on a **SEPARATE multi-relevant gold-set** — **do not mix the two recall senses**: this
    query has **5** relevant docs; the single query retrieves **2/5** in its top-5 → **recall@5 = 0.4**; the **union**
    of 3 paraphrases' top-5 retrieves **4/5** → **recall@5 = 0.8**. (HyDE above uses the single-true-doc binary recall;
    multi-query uses this 5-relevant set — two different gold-sets, stated explicitly.)
- **Numbers:** rank 8 → 2; recall@5 0 → 1 (single-doc, binary); RR **0.125 → 0.5**; multi-query recall@5 **0.4 → 0.8**
  (separate 5-relevant gold-set: 2/5 → 4/5).
- **`data/l10-rewrite.json` schema:** `{query, trueDocId, original:{rankedList:[…], trueRank:8, recallAt5:0,
  rr:0.125}, hyde:{hypotheticalDoc, trueRank:2, recallAt5:1, rr:0.5}, multiQuery:{paraphrases:[…],
  goldRelevant:[5 docIds], foundSingle:[2 docIds], foundUnion:[4 docIds], recallAt5Single:0.4, recallAt5Union:0.8}}`.
  **original/hyde** carry the single `trueDocId` (binary recall); **multiQuery** carries its own `goldRelevant` set of
  **5** ids — the two recall numbers come from two committed gold-sets, never blended.
- **Generator:** `gen_l10.py` (stdlib): RR = 1/rank; single-doc recall@5 = (trueRank ≤ 5) ∈ {0,1}; multi-query
  recall@5 = |goldRelevant ∩ retrieved-top-5| / |goldRelevant| (= 2/5 and 4/5 = 0.4, 0.8 from `foundSingle`/`foundUnion`
  over the paraphrase top-k sets). The *toy* ranks are authored; a **representative real lift** (HyDE on nfcorpus) is a
  cited/frozen number.
- **Gating:** `[C]` on RR **0.125** (≥2-dp → **coverage-caught**) and on RR **0.5** and recalls **0.4 / 0.8** (each a
  **single-decimal** → **NOT** coverage-caught, so each needs an explicit [C]-claim or a `0.50/0.40/0.80` render);
  `provenance_l10` pins `rr == 1/trueRank`, `recallAt5(single-doc) == (trueRank<=5)`, and
  `recallAt5Single/Union == |goldRelevant ∩ retrieved| / 5`. *(Exhaustive-gating rule: every displayed ≥2-dp
  intermediate on the slide + in the Book gets a `[C]`-claim, per the exhaustive `l8_deck_claims()`; the data file
  exposes each as a claimable field — the numbers listed here are only the headline ones.)*

## Frontier + lab
- **Frontier — fold into `climb-chunking` (after the taught size/overlap baseline):** **Late Chunking: Contextual
  Chunk Embeddings Using Long-Context Embedding Models** — Michael Günther, Isabelle Mohr, Daniel James Williams, Bo
  Wang, Han Xiao (Jina AI), **arXiv:2409.04701** (2024; cs.CL/cs.IR). *Why it's here:* it directly attacks the defect
  the chunking climb exposes — naïve chunking **embeds each chunk in isolation**, losing the surrounding context. Late
  Chunking **embeds all tokens of the long document first** (one long-context forward pass), and applies chunking
  **after the transformer, just before mean-pooling** ("late") — so each chunk embedding still carries the full
  document context, with **no extra training** and applicable to many long-context encoders. **VERIFICATION
  (cross-checked against the arXiv abstract):** verified claims are *embed-then-chunk (chunk after the model, before
  mean-pooling)*, *captures full contextual information*, *training-free / generic across long-context models*, *plus
  an optional dedicated fine-tuning*. Present it as the *modern fix* for the overlap-vs-context tension, **not** as the
  taught baseline. Hero figure: the isolated-chunk vs late-chunk embedding diagram. *(Alternative if a newer
  innovation is wanted: **"Adaptive Chunking: Optimizing Chunking-Method Selection for RAG"** — de Moura Júnior, Lelong
  & Blangero, **arXiv:2603.25333** (LREC 2026; cs.CL/cs.AI/cs.IR) — **verified to resolve 2026-06-16** (a real,
  document-aware chunker-selection framework: 5 intrinsic metrics, answer-correctness 62–64% → 72%). It is newer and
  less-established than Late Chunking — mark it the bleeding edge. **Late Chunking remains the safe, established
  frontier pick.**)*
- **Lab tool — canonical RAG framework = LlamaIndex; lightweight chunker demo = chonkie:** build a **retrieve → stuff
  → generate** pipeline on BEIR nfcorpus and **sweep chunk size/overlap → retrieval quality (recall@10 / nDCG@10)**,
  then add a **HyDE / multi-query** rewrite and measure the lift. *Why it's here:* it makes every L15 climb a
  measurement the student takes (the toy ranks/recalls become real curves). **LlamaIndex** (`SentenceSplitter` node
  parser + a query engine) is the canonical, widely-maintained framework backbone; **chonkie** (github.com/chonkie-inc
  /chonkie) is an *optional lightweight chunking demo* to contrast splitters. **VERIFICATION note:** both are
  *community frameworks — demos, not authority*; **verify the version/API before assigning** (RAG framework APIs churn
  fast). To stay **CPU-runnable (H5 spirit)**, the generation step uses a **small local model or a mocked generator**
  (the lab's graded core is the *retrieval-quality sweep*, which needs no GPU); a hosted LLM is optional, not required.
  *(RAGAS / LLM-as-judge evaluation is L16's tool, deliberately kept out of L10.)*
