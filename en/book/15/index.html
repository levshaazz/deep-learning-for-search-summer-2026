The Oracle

For ten lectures the Ship has done one job: find and order records. Last lecture we opened the hyperspace lanes so it could reach any passage in milliseconds. But finding the passage about the cardiac cycle is not the same as answering "how does the heart pump blood?" Today the Ship stops merely finding and learns to speak.

Ask a bare language model and it answers fluently — and sometimes confidently wrong: its knowledge is frozen at training time, it cites nothing, and it cannot tell you where it got an answer. Enter RAGdoll the Oracle: retrieval-augmented generation feeds the model the passages our lanes retrieved, so it reads before it speaks. This is the spine's first new leg in ten lectures — Generate, on top of Rank.

Confident ≠ correct

A bare LLM has three failures as a search answer. Stale: its parametric memory froze at training time, so last week's release or last night's news simply isn't there. Unciteable: it cannot point to a source, so you cannot verify it. Confident either way: a correct answer and a fabricated one come out in the same fluent, assured voice — the reader cannot tell them apart.

The fix is not a bigger model; it is grounding. Don't ask the model to know — make it read what we retrieved, then answer using only that, with citations. That is the RAG loop, and the rest of this lecture builds it.

Retrieve → augment → generate

RAG is three moves. Retrieve: run the query through everything we built (index, embeddings, the cascade, the ANN lanes) and pull the top passages. Augment: stuff those passages into the model's prompt as context. Generate: the model writes an answer grounded in that context, citing the passages. Retrieval (Lectures 3–9) sits upstream; RAG does not replace it, it consumes it.

The loop, written down

The three moves — retrieve, augment, generate — deserve to be written as one expression, because the whole rest of the lecture is just one of these arrows getting smarter. Let the query be \(q\), the corpus be a set of chunks \(\{c_1, \dots, c_N\}\), and the language model be \(p_\theta\). The loop is: first retrieve a small set \(R = \mathrm{top\text{-}k}_{c}\, s(q, c)\), the \(k\) chunks the scorer \(s\) ranks highest; then augment by concatenating them into a prompt \(x = \mathrm{prompt}(q, R)\); then generate \(a \sim p_\theta(a \mid x)\), an answer conditioned on \(q\) and the retrieved context.

Read that left to right and every later beat lands in one of three slots. Chunking decides what the elements \(c_i\) even are — you cannot retrieve a unit you never carved. Query understanding rewrites the \(q\) that goes into \(s(q, c)\), so the scorer aims at the real question. Re-ranking swaps a cheap \(s\) for an expensive-but-accurate one on the shortlist \(R\). Routing picks which corpus or prompt to use. Every technique in this lecture is a sharpening of one arrow.

Two properties of the loop matter more than any single trick. First, it is non-parametric: the knowledge lives in the corpus, not in \(\theta\), so updating the answer means updating the index — no retraining, no stale weights. Lewis et al. (NeurIPS 2020) named this retrieval-augmented generation precisely to contrast it with a model's frozen parametric memory. Second, it is bounded by retrieval: if the true answer is not in \(R\), no amount of generation can recover it. The generator inherits the recall floor of the retriever — which is exactly why the nine lectures before this one were not a detour.

So when the Oracle speaks, it is never speaking from memory. It is reading \(R\) aloud, in its own words, with citations back to the \(c_i\) it read. That is the whole contract: answer using only what was retrieved, and say where each claim came from. Hold that sentence; the catch beat at the end of the lecture is what happens when the contract is honored but \(R\) was garbage.

Two memories, not one bigger one

The loop you just wrote down has a top-\(k\) baked into it. Step back one notch, before that shortcut, and the shape of the whole idea appears. Treat the retrieved passage as a latent passage \(z\) and write the answer distribution as a marginal over it: \( p(y\mid x)=\sum_{z\in\mathcal{Z}}p_{\eta}(z\mid x)\;p_{\theta}(y\mid x,z) \), with the retriever \(p_{\eta}\) choosing \(z\) out of the index \(\mathcal{Z}\) and the generator \(p_{\theta}\) reading the question and the passage together. Set that beside the bare model, \( p_{\theta}(y\mid x) \): one term, no \(z\), every fact obliged to live inside \(\theta\).

Now «grounding, not scale» stops being a slogan and becomes bookkeeping. The two levers are two different factors of one product. Growing \(\theta\) sharpens \(p_{\theta}\) — it makes the reading better — but it cannot conjure the sum, and a corpus that is private, or newer than the training run, was never inside \(\theta\) to be sharpened in the first place. Two properties fall out of the same line for free. Freshness: to change the answer you rebuild the index, not the weights. Citability: \(z\) is a pointer to a document that exists, so «where did that come from» has an answer that is not a memory.

The equation also draws the map of everything ahead. Chunking, query rewriting and routing are all edits to \(p_{\eta}\) — they change which \(z\) gets picked. The prompt and faithfulness are edits to \(p_{\theta}\) — they change what the Oracle does with the \(z\) it got. And say the honest simplification aloud, since it is the version you will actually build: no system sums over the whole index, so the marginal is replaced by the top-\(k\) set \(R\) you just defined. That swap is what makes the loop runnable, and it is also the exact seam where the recall floor gets in.

The token budget

How much can you stuff into the prompt? The context window is finite, and that cap is why ranking matters — you can only afford the very best passages.

Take a context window of \(4096\) tokens. The system prompt costs \(200\), the query \(30\), and you reserve \(512\) for the answer. Each chunk is \(256\) tokens, so the most chunks you can fit is \(k_{\max} = \lfloor (4096 - 200 - 30 - 512)/256 \rfloor = \lfloor 3354/256 \rfloor = \mathbf{13}\). At \(k=4\): stuffed \(= 4\times 256 = 1024\), prompt total \(= 200+30+1024 = 1254\), headroom \(= 4096-1254 = 2842\).

So \(k \le 13\): the window caps how much you can retrieve. Spend that budget on the best passages your ranker can find — which is exactly why every lecture before this one mattered.

Why those chunks rank as they do

The anchor trace scored the candidates for "how does the heart pump blood?" and ranked doc_cardiac_cycle, doc_circulatory, doc_valves as the top three, with doc_anatomy trailing as a weaker fourth. Those rankings did not fall from the sky; they are cosine similarities between the query vector and each chunk vector, recomputed here so you can check every digit by hand. This is the retrieve arrow, exact.

Project everything onto four toy dimensions — pump/contraction, anatomy/structure, flow/vessels, valves/one-way. The query "how does the heart pump blood?" lands at \(q = (3, 2, 1, 1)\): heavy on pump, lighter on the rest. Each candidate chunk is its own vector. Cosine is \(\cos(q, d) = \dfrac{q \cdot d}{\lVert q \rVert\,\lVert d \rVert}\), and \(\lVert q \rVert = \sqrt{3^2 + 2^2 + 1^2 + 1^2} = \sqrt{15}\).

doc_cardiac_cycle \(= (1, 2, 1, 2)\): dot \(= 3{+}4{+}1{+}2 = 10\), \(\lVert d \rVert = \sqrt{10}\), so \(\cos = \dfrac{10}{\sqrt{15}\,\sqrt{10}} = \mathbf{0.8165}\). doc_circulatory \(= (1, 2, 2, 2)\): dot \(= 11\), \(\lVert d \rVert = \sqrt{13}\), \(\cos = \dfrac{11}{\sqrt{15}\,\sqrt{13}} = \mathbf{0.7877}\). doc_valves \(= (1, 5, 0, 2)\): dot \(= 15\), \(\lVert d \rVert = \sqrt{30}\), \(\cos = \dfrac{15}{\sqrt{15}\,\sqrt{30}} = \mathbf{0.7071}\).

Rounded to two places these are the scores the trace shows for the top three, and they decide the order: cardiac-cycle first, circulatory second, valves third. doc_anatomy scores lower still — kept only as the 4th and weakest chunk at the anchor's \(k = 4\) — the structural fact the question did not really ask for, carried along but contributing least. The same machinery you built in Lectures 6–7 (embeddings) and 10 (the bi-encoder's dot product) is doing the work; RAG adds no new retrieval math, it just consumes it.

Notice that doc_valves has the largest raw dot product (\(15\)) yet the smallest cosine. That is length normalisation earning its keep: the valves chunk is a long, anatomy-heavy vector that happens to overlap the query's tiny anatomy component a lot, but cosine divides that out and asks only about direction. Without the \(\lVert d \rVert\) in the denominator, a verbose off-topic chunk would out-rank a short on-point one — the exact failure cosine was chosen to prevent.

Bigger windows, more chunks — not free

The previous beat fixed the window at \(4096\) tokens and found \(k_{\max} = 13\). But context windows have grown enormously — \(8\mathrm{k}\), \(32\mathrm{k}\), \(128\mathrm{k}\) and beyond. Does the budget pressure just disappear? Hold the same fixed overhead — system \(200\), query \(30\), \(512\) reserved for the answer, \(256\)-token chunks — and sweep the window. The formula is unchanged: \(k_{\max} = \lfloor (\text{ctx} - 200 - 30 - 512)/256 \rfloor\).

\(4096\) → \(\lfloor 3354/256 \rfloor = \mathbf{13}\) chunks. \(8192\) → \(\lfloor 7450/256 \rfloor = \mathbf{29}\). \(32768\) → \(\lfloor 32026/256 \rfloor = \mathbf{125}\). \(128000\) → \(\lfloor 127258/256 \rfloor = \mathbf{497}\).

So \(k_{\max}\) grows roughly linearly with the window: double the context, roughly double the chunks you can fit. A \(128\mathrm{k}\) window holds nearly \(500\) chunks — it can feel like ranking stops mattering and you can simply stuff everything. That feeling is a trap. Every extra chunk is more tokens to encode and attend over, so latency and cost climb with \(k\); and a longer prompt is a diluted prompt.

The dilution has a name: "lost in the middle" (Liu et al., Lost in the Middle: How Language Models Use Long Contexts, TACL 2024, arXiv:2307.03172). Models attend most reliably to the start and end of a long context and skim the middle, so burying the one relevant chunk at position \(247\) of \(497\) can be worse than handing over a tight top-\(5\). A bigger window raises the ceiling on how much you may retrieve; it does not raise the quality of an unranked dump. The job of the ranker — keep the best \(k\), in the best order, near the edges — survives every window expansion.

Practically: pick \(k\) for the question, not for the window. A factoid lookup might need \(k = 3\); a synthesis across sources might want \(k = 20\). Treat \(k_{\max}\) as the hard ceiling the budget imposes, and let ranking choose the actual \(k\) underneath it. The window says how much you may; the ranker says which ones you should.

How you cut decides what you can find

Before retrieval can find a passage, chunking must have carved it. The corpus is split into fixed-size pieces, each embedded and indexed — and you can only ever retrieve a whole chunk. So the cut decides what is findable: if the answer is split across two chunks, no single retrieval brings it back whole. Chunk Norris chops the scroll into equal passages; Tokenosaurus (Lecture 2) reminds us the pieces are sub-word tokens, not characters.

Size, overlap, by hand

Take a \(1000\)-token document whose answer lives in tokens \([380, 470]\). The chunk count is \(\lceil (L - \text{overlap})/(\text{size} - \text{overlap}) \rceil\), and "found" is binary answer-containment: does any one chunk contain the whole span?

size=200, overlap=0 → \(\lceil 1000/200 \rceil = \mathbf{5}\) chunks, with windows \([0,200],[200,400],[400,600],\dots\) The answer straddles boundary \(400\) — \(20\) tokens in chunk 2, \(70\) in chunk 3 — so no chunk holds it whole: recall@3 = 0. size=200, overlap=50 → \(\lceil 950/150 \rceil = \mathbf{7}\) chunks; the window \([300,500]\) contains \([380,470]\) whole: recall@3 = 1.0.

Overlap costs storage — more chunks, each fatter — and buys recall: the answer no longer falls between the cracks. That tension is exactly what the frontier, Late Chunking (Günther et al., 2024), attacks: it embeds the whole long document first and chunks after the transformer, so each chunk embedding still carries the full document's context — no overlap-vs-context tradeoff.

Sweep the overlap

The worked example showed two settings; let me run the full sweep so you can watch the recall curve and the storage curve pull against each other. Same \(1000\)-token document, same gold answer span \([380, 470]\), same fixed chunk size \(200\) — only the overlap moves: \(0, 50, 100, 150\). "Found" stays binary answer-containment: does any window hold \([380, 470]\) whole?

overlap \(0\) → step \(200\), \(\lceil 1000/200 \rceil = 5\) chunks; windows \([200,400]\) and \([400,600]\) both straddle boundary \(400\) → no chunk holds the span → recall@3 \(= 0\). overlap \(50\) → step \(150\), \(\lceil 950/150 \rceil = 7\) chunks; window \([300,500]\) holds it → recall@3 \(= 1.0\). overlap \(100\) → step \(100\), \(9\) chunks, window \([300,500]\) → recall@3 \(= 1.0\). overlap \(150\) → step \(50\), \(17\) chunks, window \([300,500]\) → recall@3 \(= 1.0\).

The recall column reads \(0 \to 1.0 \to 1.0 \to 1.0\): once overlap is large enough to slide a window across the \(400\) boundary, the answer is captured and stays captured. The first non-zero overlap does all the rescuing; more overlap after that buys nothing for this span. But the storage column climbs the whole way — \(5 \to 7 \to 9 \to 17\) chunks — because each extra chunk is embedded and indexed and searched.

That is the chunking tradeoff in one table. Recall is monotone non-decreasing in overlap (more overlap can never lose a span you already caught), so it is tempting to crank overlap high. Resist: at overlap \(150\) you store more than three times the chunks of the overlap-\(0\) baseline for the same recall, inflating the index, the embedding bill, and the per-query candidate set. The right overlap is the smallest one that closes the boundary-straddle gap for your typical answer length — here, \(50\).

And notice the deeper problem the sweep cannot fix: every one of these chunks is embedded in isolation, as if the surrounding document did not exist. Overlap papers over the boundary cut but still hands the encoder a context-free window. That residual defect — not the boundary, but the isolation — is what the frontier technique two beats from now attacks head-on.

Four ways to cut

Fixed-size chunking with overlap is the baseline, not the only option. How you cut is a design space, and four strategies span it from cheapest-and-dumbest to clever-and-contextual. Each makes a different bet about where the natural seams of meaning are.

Fixed-size cuts every \(N\) tokens at hard boundaries, optionally with overlap. It is the cheapest and ignores all structure — a fine fast baseline for uniform text, and the one you just worked through. Recursive respects a separator hierarchy: split on paragraphs first, then sentences, then words, descending only until each piece fits \(N\). It is still cheap and keeps natural boundaries intact, which is why it is the default for structured prose, Markdown, and code where a mid-sentence or mid-function cut would be destructive.

Semantic chunking spends a little more: it embeds each sentence and starts a new chunk wherever adjacent-sentence similarity drops below a breakpoint threshold — typically a percentile of the adjacent-sentence distance distribution (e.g. the 95th percentile) rather than any tiny dip, which is the method's key knob, trading chunk count against coherence — so a chunk boundary lands at a genuine topic shift rather than an arbitrary token count. It costs one embedding pass over the sentences, and it shines on topic-shifting documents where fixed cuts would slice an idea in half. Late chunking is the frontier entry, kept for the next beat: embed the whole long document first, then chunk after the transformer — so each chunk embedding still carries the full document's context.

The throughline is that chunking is the only stage where you can inject document structure into a retrieval system that otherwise sees a flat bag of vectors. Fixed-size throws that structure away; recursive and semantic preserve increasing amounts of it; late chunking preserves the cross-chunk context that all three earlier methods discard. The more structure you keep, the more the retrieved unit looks like a coherent answer rather than an arbitrary slice.

There is no universally best cut — the right strategy depends on the corpus. The next beat lays the four side by side so you can match a strategy to a document type; then the frontier beat shows why even the cleverest cut still leaves one defect that only a change in when you embed can fix.

Which cut for which corpus

Put the four strategies in one comparison and the choice becomes a matter of matching cost to the corpus, not chasing a winner. Read each row as how it cuts → what it costs → when to reach for it.

Fixed-size — cuts every \(N\) tokens at hard boundaries, optionally with overlap. Cost: cheapest. Reach for it on uniform text where you want a fast baseline, and pair it with overlap to soften the boundary straddle you saw in the sweep. Recursive — splits on a separator hierarchy (paragraph → sentence → word) until each piece fits. Cost: cheap. Reach for it on structured prose, Markdown, or code, where natural boundaries carry meaning and a blind cut would mangle a sentence or a function.

Semantic — embeds sentences and starts a new chunk where adjacent-sentence similarity drops. Cost: moderate, one embedding pass over the sentences. Reach for it on topic-shifting documents where fixed cuts split a single idea across two chunks. Late chunking — embeds all tokens of the long document first, then chunks after the transformer, before mean-pooling. Cost: needs a long-context encoder, but it is training-free. Reach for it when chunk embeddings must keep full-document context, which is exactly the isolated-chunk defect the earlier three share.

Reading top to bottom, you are trading cost for context-awareness: each row keeps a little more of the document's structure than the one above, and pays a little more to do it. Fixed-size knows nothing but token counts; recursive knows the document's punctuation; semantic knows where its topics turn; late chunking knows the whole document at once. The descending order of the matrix is the ascending order of how much meaning survives the cut.

A practical default many systems land on: recursive chunking by paragraph and sentence, with a modest overlap, as the everyday workhorse — cheap, structure-aware, and robust. Escalate to semantic when topic drift inside documents is hurting recall, and to late chunking when you can afford a long-context encoder and the isolated-chunk context loss is the bottleneck. None of these is the right answer in the abstract; the corpus decides.

Late chunking: embed first, cut after

Every chunking strategy so far shares one hidden flaw, and it is not the boundary cut that overlap rescues. It is isolation: each chunk is fed to the encoder alone, so its embedding never sees the sentences around it. A chunk that says "it then contracts to eject the blood" has no idea what "it" is — the antecedent lived two chunks back. The embedding is contextually blind, and no amount of overlap restores the full document's context to every chunk.

Late chunking (Günther, Mohr, Williams, Wang & Xiao, Jina AI, arXiv:2409.04701, 2024) inverts the order. Instead of chunk-then-embed, it does embed-then-chunk: run the whole long document through a long-context transformer in one forward pass, so every token's representation is contextualised by the entire document; only then apply the chunk boundaries, pooling the already-contextual token vectors within each chunk. The cut happens late — after the transformer, just before mean-pooling — hence the name.

The payoff is that "it" in our example is encoded while the model can still see "the ventricle" upstream, so the chunk's embedding carries the disambiguating context even though the chunk text alone is ambiguous. You get chunk-sized retrieval units with document-sized context behind each vector — the recall benefit of long context without the "lost-in-the-middle" dilution of actually stuffing the whole document into the generator's prompt.

Two properties make it attractive rather than just clever. It is training-free: you reuse an existing long-context embedding model unchanged — no fine-tuning, no new labels — and simply change when you pool. And it is generic: it applies across many long-context encoders, so it is a method you bolt onto your pipeline, not a model you must adopt. The cost is the long-context forward pass over the whole document, which is why it is a frontier choice rather than the everyday default. And one hard limit: the overlap-versus-context tradeoff vanishes only within the encoder's context window — a document longer than that window must itself be macro-split first, and the paper's long late chunking variant re-introduces a bounded overlap between those macro-windows.

Place it correctly in your mental map: overlap fixes the boundary defect, semantic chunking fixes the topic-split defect, and late chunking fixes the isolation defect that all the cut-then-embed methods leave behind. It is the modern answer to the overlap-versus-context tension the sweep exposed — not a replacement for the taught baseline, but the next move once the baseline's isolated-chunk context loss becomes your bottleneck.

Index one thing, embed another

Chunking quietly assumed one thing: the unit you embed is the unit you return. Multi-representation indexing breaks that assumption. You can index a proxy for a chunk — a summary, a generated question, a different granularity — and still hand the generator the full original. The vector you search and the text you read no longer have to be the same object.

The cleanest version is summary indexing. For each long document, generate a short summary, embed that, and store it in the index; but keep a pointer back to the full document. At query time you match against the crisp summary vectors — which are dense with topic signal and free of the boilerplate that dilutes a full-text embedding — and on a hit you retrieve the whole document the summary points to. You search small and clean, then return large and complete.

A symmetric trick is hypothetical-question indexing: for each chunk, generate a handful of questions it could answer, embed the questions, and index those. Now an incoming query is matched question-to-question rather than question-to-passage, closing the shape mismatch between a short query and a declarative passage — the same vocabulary-gap intuition that HyDE exploits, but precomputed and baked into the index instead of generated per query.

And the granularity itself can be multiple: index small precise chunks for matching but return their larger parent section for context — small-to-big retrieval. You get the precision of a tight chunk in the scorer and the completeness of a full section in the prompt, sidestepping the recall-versus-context tension from a different angle than late chunking does.

You have met one extreme of this idea already: in Lecture 12, ColBERT indexed per-token representations and scored with late interaction, the finest-grained multi-representation of all. The lesson generalises — the index entry is a handle you design, not a fixed fact. Choose the representation that matches best, then return the representation that reads best.

RAPTOR: a tree of summaries

Summary indexing kept one summary per document. But questions arrive at different altitudes: "what is the systolic phase?" is a leaf-level detail, while "summarise how the cardiovascular system works" is a whole-corpus overview. A flat index of chunks answers the first well and the second badly — no single chunk is the overview. RAPTOR (Sarthi, Abdullah, Tuli, Khanna, Goldie & Manning, ICLR 2024, arXiv:2401.18059) builds an index that answers both.

The construction is recursive. Start with the leaf chunks. Cluster semantically similar chunks together, summarise each cluster with the model into a higher-level node, and embed those summaries. Then recurse: cluster the summaries, summarise them, and climb again — until you reach a single root that summarises everything. The result is a tree where leaves are raw passages and every internal node is an abstractive summary of its subtree.

One detail the toy figure flattens: the paper's clustering is soft, not a hard partition. RAPTOR fits a Gaussian mixture model over UMAP-reduced embeddings, so a single chunk can belong to several clusters at once and feed several parent summaries. The clean \(8 \to 3\) fan-in below is therefore a hard-partition simplification for the picture; in the real algorithm the levels overlap.

In the toy illustration the tree has three levels: \(8\) leaf chunks cluster and summarise into \(3\) mid-level nodes, which summarise into \(1\) root — depth \(3\). Each level up is coarser and more abstract; each level down is finer and more literal.

Retrieval is the payoff. Instead of searching only the leaves, you index every node at every level in one flat collection and retrieve across all of them. A broad question matches a high summary node and gets the synthesised overview; a narrow question matches a leaf and gets the precise passage. One index, one query path, but answers calibrated to the altitude of the question — no need to guess in advance whether the user wants the forest or a single tree.

RAPTOR is multi-representation indexing taken vertical: where summary indexing gave you one proxy per document, RAPTOR gives you a ladder of proxies from literal to abstract, all searchable at once. It pairs naturally with everything in this lecture — chunk the leaves however you like, route altitude-sensitive queries toward the right level, and re-rank the mixed-altitude shortlist. The tree is just a richer thing to retrieve from.

Hear the real question

Retrieval can only match the words it is given — and the captain's words are rarely the corpus's words. A short, vague query ("how does the heart pump blood?") misses a document that says "cardiac cycle, ventricular systole." HyDE writes a hypothetical answer, embeds that, and the true doc rises to rank \(2\) → recall@5 \(= 1\), RR \(= 1/2 = \mathbf{0.5}\). Multi-query (a separate \(5\)-relevant gold-set). The single query retrieves \(2/5\) → recall@5 \(= \mathbf{0.4}\); the union of \(3\) paraphrases retrieves \(4/5\) → recall@5 \(= \mathbf{0.8}\).

HyDE closes the vocabulary gap by searching with answer-shaped text; multi-query widens coverage by asking the same thing several ways. Both lift recall without touching the retriever — they just feed it a better query.

The vocabulary gap

Why does query rewriting help at all? Because of a gap that sits between how people ask and how documents answer. A user types "how does the heart pump blood?" — short, plain, everyday. The authoritative passage says "the cardiac cycle alternates systole and diastole; ventricular contraction ejects blood." They mean the same thing and share almost no words. That mismatch is the vocabulary gap.

Lexical retrievers like BM25 (Lecture 3) feel it most sharply: with no token overlap on systole or ventricular, the relevant passage scores near zero and never surfaces. Dense retrievers (Lectures 6–7) soften the gap — pump and contraction land near each other in embedding space — but they do not erase it. A two-word query is a thin, low-information probe; the relevant document is a dense, jargon-rich paragraph. Even in vector space, a short query and a long passage are different shapes, and that shape mismatch costs recall.

The gap also runs the other way: queries are often under-specified. "How does it work?" assumes a referent the retriever cannot see; "the best approach" assumes a task. The retriever matches the literal words, not the unstated intent, so a vague query retrieves vaguely. The captain's words are rarely the corpus's words, and the retriever can only match the words it is given.

Query understanding is the family of fixes that all share one move: change the query before retrieving so it aims at what was really meant. You can expand it with related terms, rewrite it into the corpus's register, generate a hypothetical answer and search with that (HyDE), ask it several ways and fuse the results (multi-query, RAG-Fusion), break it into parts (decomposition), or abstract it to a principle (step-back). Every one of these leaves the retriever untouched and simply feeds it a better-aimed query.

Keep the loop's first arrow in mind: retrieval is \(R = \mathrm{top\text{-}k}_c\, s(q, c)\). Query understanding never touches \(s\) or the corpus; it edits the \(q\) that goes in. That is what makes it cheap and composable — it sits entirely upstream of the index, so you can stack it on top of any retriever you already built.

Ask it several ways

A single phrasing of a question is a single throw of a dart. Sometimes it lands; sometimes the one relevant passage uses a synonym your phrasing missed. Multi-query hedges that bet: have the model rewrite the query into several paraphrases, retrieve for each, and take the union of the results. Where one phrasing covers one corner of the relevant set, three phrasings between them cover more.

Take our running query and let the model produce three variants: "How does the heart pump blood?", "What happens during the cardiac cycle?", and "Explain ventricular systole and diastole." Each paraphrase reaches for a different patch of the corpus — the first stays in everyday register, the second names the cycle, the third names systole and diastole outright. A passage indexed under systole that the plain query missed is squarely in reach of the third paraphrase.

The retrieval step is unchanged — you run the same retriever, just with more queries — and the only new step is the union at the end: pool the candidate sets, dedupe, and you have a recall-boosted shortlist. Because it widens coverage rather than re-scoring, multi-query is the recall-first member of the query-understanding family; you cast a wider net and let a later re-ranker tighten the catch.

It is not free. Three paraphrases mean three retrievals, so latency and cost roughly triple, and the union can drag in mild off-topic drift if a paraphrase wanders. The standard discipline is to keep the paraphrase count small (three to five), to dedupe aggressively, and — crucially — to combine the lists by rank rather than naively concatenate them, which is exactly the fusion problem the next beats formalise.

The next beat measures the lift on a small gold-set so you can see the recall move in numbers; then RAG-Fusion replaces the naive union with the reciprocal-rank fusion you already met in Lecture 3, turning "ask it several ways" into a principled consensus over ranked lists.

Multi-query, by the numbers

Let me put a number on the union. This is a different gold-set from the HyDE example — never blend the two — because multi-query is judged on a query with several relevant documents, not one. Here the gold set has \(5\) relevant docs: gold_cycle, gold_systole, gold_ventricle, gold_diastole, gold_output. Recall@5 is the fraction of those five that appear in the retrieved top-5.

The single query retrieves only gold_cycle and gold_systole in its top-5 → \(2/5 \Rightarrow\) recall@5 \(= \mathbf{0.4}\). Now run all three paraphrases and union their top-5 lists: between them they surface gold_cycle, gold_systole, gold_ventricle, and gold_diastole → \(4/5 \Rightarrow\) recall@5 \(= \mathbf{0.8}\).

The single phrasing found two of five; the union of three found four of five — recall doubled, from \(0.4\) to \(0.8\), with no change to the retriever or the index. The two extra docs (gold_ventricle, gold_diastole) were reachable only because a different paraphrase used the word that matched each one. The everyday-register query never said ventricle; the third paraphrase did, and that is the doc it pulled in.

One relevant doc stayed missed: gold_output slipped through all three nets. That is the honest ceiling of paraphrasing — it widens coverage along the directions the model thinks to vary, but a relevant doc phrased in a register none of the paraphrases hit still escapes. Multi-query raises the recall floor; it does not guarantee perfect recall, and chasing the last document by piling on paraphrases hits diminishing returns fast.

Two design notes the numbers make concrete. First, the lift comes from diversity among paraphrases — three near-identical rewrites would have retrieved the same two docs and bought nothing; the gain is proportional to how differently the paraphrases probe the corpus. Second, the union here was a naive set-union over top-5 lists; the next beats replace it with rank-aware fusion, which keeps the same recall lift while restoring a sensible order over the pooled candidates.

HyDE: search with the answer

Multi-query attacks the vocabulary gap by varying the question. HyDE attacks it from the opposite end — by manufacturing an answer. The acronym unpacks to Hypothetical Document Embeddings (Gao, Ma, Lin & Callan, Precise Zero-Shot Dense Retrieval without Relevance Labels, ACL 2023, arXiv:2212.10496), and the move is delightfully circular: ask the model to write a plausible answer first, then search for the real documents that look like that answer.

Why does writing a fake answer help find a real one? Because of the shape mismatch from the vocabulary-gap beat. A query is short and interrogative; a relevant passage is long and declarative. Embedding a two-word question and a dense paragraph puts them in different neighbourhoods of vector space even when they are about the same thing. A hypothetical answer, though, is itself long and declarative — it has the same shape and register as the documents you want — so its embedding lands much closer to the true passage than the bare query's does.

Concretely: the model writes a hypothetical paragraph rich with the right register — "the cardiac cycle drives blood flow: during ventricular systole the ventricles contract, ejecting blood; pressure gradients and one-way valves keep circulation moving." That text need not be factually perfect — it is never shown to the user. It is a lure: you embed the lure and retrieve the real documents nearest to it. The hallucinated specifics do not matter; the topical shape is what pulls the true passage up.

On the single-true-doc model the lift is sharp. The bare query ranks the true doc \(8\)th → recall@5 \(= 0\), reciprocal rank \(= 1/8 = \mathbf{0.125}\). Embed the hypothetical answer instead and the true doc rises to rank \(2\) → recall@5 \(= 1\), reciprocal rank \(= 1/2 = \mathbf{0.5}\). The query the retriever actually saw was answer-shaped, so it aimed where the answers live.

One caveat keeps "shape beats accuracy" honest: it holds only when the model can place the answer in roughly the right topical region. For a query about a rare or novel entity, a fresh fact, or a domain the LLM never saw, the hypothetical is wrong in shape, not just in detail — it lands in the wrong neighbourhood of vector space, and HyDE can then rank the true document lower than the bare query. That is exactly why HyDE pairs with a strong retriever rather than replacing it: when the model can guess the right neighbourhood the lure works, and when it cannot the retriever still has to carry the case.

HyDE and multi-query are the two ends of query understanding: HyDE makes the query look like an answer; multi-query makes several queries to cover more phrasings. They compose — write several hypothetical answers, embed each, union the hits — and both leave the retriever untouched, paying only an extra LLM call to reshape the probe. The lift magnitudes are dataset-dependent (the paper reports representative gains, not a universal constant), but the mechanism is exactly what the toy numbers show: a better-shaped query finds the true doc sooner.

RAG-Fusion: consensus over lists

Multi-query left us with several ranked lists and a crude way to merge them — a naive set-union that throws away all the rank information. RAG-Fusion fixes the merge: keep multi-query's several paraphrase retrievals, but combine their ranked lists with Reciprocal Rank Fusion instead of a flat union. You already built RRF in Lecture 3 for fusing lexical and dense rankers; here it does the same job across paraphrase queries.

Recall the rule: a document's fused score is \(\mathrm{RRF}(d) = \sum_{\text{lists}} \dfrac{1}{k + \mathrm{rank}_d}\), summed over every list in which \(d\) appears, with a smoothing constant \(k = 60\). A document near the top of a list contributes a large \(\frac{1}{k+\mathrm{rank}}\); a document buried deep contributes a tiny one; a document absent from a list contributes nothing. Sum across lists and re-sort — that is the whole method.

The property that makes RRF the right tool here is consensus. A document ranked second in one paraphrase's list and first in another accumulates contributions from both, and that doubled-up agreement can beat a document that tops a single list but appears in no other. RRF rewards documents the paraphrases agree on — exactly the signal you want when you deliberately asked the same question several ways. Broad agreement across rephrasings is a stronger relevance vote than one paraphrase's lucky top hit.

Two practical virtues carry over from Lecture 3. RRF needs no score calibration — it consumes only ranks, so it fuses lists from wildly different retrievers (BM25, dense, a re-ranker, three paraphrases) without normalising incomparable score scales. And the constant \(k = 60\) damps the influence of any single high rank, so no one list can dominate the fusion on its own. The next beat works a small fusion by hand so you can watch the consensus document win on the arithmetic.

Step back and see the pattern: multi-query supplies the diversity (several probes of the corpus), and RAG-Fusion supplies the aggregation (a rank-aware consensus over what they found). Together they turn "ask it several ways" from a recall hack into a principled re-ranking — the same fusion idea from classical IR, now wrapped around an LLM that writes the paraphrases.

Fusion, by hand

Let me run a small RAG-Fusion by hand so the consensus win is arithmetic, not assertion. Two paraphrases each return a top-5. List A is \([\,\texttt{circulatory},\ \texttt{cardiac\_cycle},\ \texttt{anatomy},\ \texttt{valves},\ \texttt{pressure}\,]\); list B is \([\,\texttt{cardiac\_cycle},\ \texttt{systole},\ \texttt{circulatory},\ \texttt{diastole},\ \texttt{output}\,]\). Score each doc with \(\mathrm{RRF}(d) = \sum \frac{1}{60 + \mathrm{rank}}\), \(k = 60\).

Two documents appear in both lists, so only they accumulate two contributions; everything else appears once. Watch the head-to-head between the two co-occurring docs — circulatory, which tops list A, and cardiac_cycle, which tops list B but sits second in A.

cardiac_cycle is rank \(2\) in A and rank \(1\) in B: \(\mathrm{RRF} = \frac{1}{60+2} + \frac{1}{60+1} = \frac{1}{62} + \frac{1}{61} = \mathbf{0.0325}\). circulatory is rank \(1\) in A and rank \(3\) in B: \(\mathrm{RRF} = \frac{1}{60+1} + \frac{1}{60+3} = \frac{1}{61} + \frac{1}{63} = \mathbf{0.0323}\). Every single-list doc scores below both: systole at \(\frac{1}{62}\), anatomy at \(\frac{1}{63}\), and the rest lower still.

So the fused order puts cardiac_cycle first — even though it did not top list A. It won by consensus: ranking near the top of both paraphrases beat circulatory's single first place. That is the whole point of fusing rephrasings — a document the paraphrases agree on outranks one that merely tops a single list, because broad agreement is the stronger relevance signal. The margin is razor-thin (\(0.0325\) versus \(0.0323\)), exactly because RRF's \(k = 60\) deliberately compresses rank differences so no single list runs away with the result.

Notice what fusion did that the naive set-union of the multi-query beat could not: it produced an order. The union gave you a recall-boosted bag with no ranking; RRF gives you the same boosted candidate set and sorts it by cross-paraphrase agreement, ready to feed straight into the token budget — best chunks first, as the lost-in-the-middle beat demanded. Diversity from multi-query, order from fusion.

Decomposition: split the question

Some questions ask two things at once. "Does the heart pump faster during exercise, and what controls that rate?" bundles a fact (does the rate rise?) and a mechanism (what controls it?). A single retrieval must find one chunk that satisfies both — and often no such chunk exists, because the two facts live in different passages. Decomposition breaks the compound query into sub-questions, retrieves for each, and assembles the answer from the parts.

Make the failure concrete with binary answer-containment. Suppose the rate-increase fact lives in one chunk and the rate-control fact in another. Retrieving for each sub-question on its own succeeds — call the per-sub recalls \(\text{recall}_{\text{sub}} = [1, 1]\), each sub-answer sits cleanly in its own chunk. But ask the joint question and demand a single chunk containing both facts, and \(\text{recall}_{\text{joint}} = 0\): no chunk holds both. The compound query fails not because the facts are missing, but because no single retrieval unit carries them together.

Decomposition recovers what the joint query lost. Split into "Does heart rate increase during exercise?" and "What controls heart rate?"; retrieve each separately; each pulls back its own supporting chunk; then the generator stitches the two retrieved facts into one answer. Two retrievals at \(\text{recall} = 1\) each beat one joint retrieval at \(\text{recall} = 0\) — the compound question is recoverable only once you stop asking for it in one shot.

The pattern generalises to any multi-hop question — "compare X and Y on dimension Z", "what changed between version A and version B?" — where the evidence is necessarily spread across documents. The model proposes the sub-questions, you run the retrieve loop once per sub-question, and you fan the results back into a single grounded answer. Each sub-question is an ordinary RAG query; decomposition is just the orchestration on top.

There is a cost and a discipline. More sub-questions mean more retrievals and a longer prompt, so decompose only when the question genuinely has separable parts — over-splitting a simple question wastes calls and can fragment a coherent answer. The skill is recognising compound intent: when one retrieval is being asked to satisfy two independent information needs, split it; when the question is genuinely atomic, leave it whole.

Step-back: ask the principle first

Decomposition splits a question sideways into parts. Step-back prompting moves upward instead: before answering a narrow, specific question, abstract it into a more general one, retrieve the underlying principle, and then use that principle to answer the specific. The move is named for the mental gesture — take a step back from the detail to see the rule it is an instance of (Zheng, Mishra, Chen, Cheng, Chi, Le & Zhou, Take a Step Back, arXiv:2310.06117, 2023).

Concretely: the specific question is "Why did my heart rate hit 180 bpm running up the stairs?" That exact number is too idiosyncratic to match any document — no passage discusses your stair-climb. Step back to the generic version, "What physiological mechanism regulates heart rate under exertion?", and retrieve the principle: "the sympathetic nervous system raises heart rate during exertion (autonomic regulation of cardiac output)." Now answer the specific question grounded in that retrieved principle.

Why does abstracting help retrieval? A hyper-specific query is a poor match because the corpus is written at the level of principles, not your individual instance. The generic question is phrased the way the explanatory passage is phrased, so it retrieves cleanly — the same vocabulary-gap logic again, but the gap here is one of specificity rather than synonym. Once the principle is in hand, applying it to the specific case is something the generator does well; what it could not do was retrieve evidence for an instance the corpus never mentions.

Step-back pairs naturally with reasoning-heavy questions where the answer is deduced from a general rule rather than looked up directly. Math word problems, physics scenarios, diagnostic questions — anything of the form "given this specific situation, what happens?" — benefit, because the retrieval target is the governing law, not the particular case. It is decomposition's vertical cousin: decomposition fans out to sibling sub-questions; step-back climbs to the parent principle.

Notice the through-line across this whole query-understanding cluster: HyDE reshapes a query to look like an answer, multi-query and RAG-Fusion widen and fuse phrasings, decomposition splits compound intent, and step-back abstracts to a retrievable principle. Each is a different transformation of \(q\) before \(s(q, c)\) ever runs — and the next beats turn from transforming the query to choosing where to send it.

The query-translation matrix

Five query-translation techniques now sit on the table; lay them side by side so you can pick by symptom rather than by fashion. Read each as what it transforms → what it fixes → what it costs.

Multi-query — rewrites the query into several paraphrases and unions the hits. Fixes: a single phrasing missing synonym-indexed docs. Costs: \(k\times\) the retrievals. RAG-Fusion — the same paraphrases, but merged by Reciprocal Rank Fusion instead of a flat union. Fixes: the union's lack of order; rewards cross-paraphrase consensus. Costs: the same retrievals plus a cheap rank-merge. HyDE — generates a hypothetical answer and embeds that. Fixes: the question-vs-passage shape mismatch. Costs: one extra LLM generation per query.

Decomposition — splits a compound question into sub-questions, retrieves each, recombines. Fixes: no single chunk contains all the facts a multi-part question needs. Costs: one retrieve loop per sub-question. Step-back — abstracts a specific question to a general principle, retrieves the principle, then answers the specific. Fixes: a hyper-specific query that matches no instance-level document. Costs: one extra generation plus a second retrieval.

Two organising axes cut across the five. One axis is count: HyDE and step-back keep a single transformed query, while multi-query, RAG-Fusion, and decomposition issue several and must then aggregate. The other is direction of the transform: multi-query and RAG-Fusion go sideways (more phrasings of the same question), decomposition goes sideways into parts, step-back goes up (to a principle), and HyDE goes across (from question-shape to answer-shape). Place a new technique on these two axes and you usually know what it is good for.

And they compose. A serious pipeline might step back to fetch the governing principle, decompose the specific question into parts, run multi-query on each part, and fuse all the lists with RRF — every stage a transformation of \(q\) before the retriever ever runs. The matrix is not a menu of one-of; it is a toolbox you stack by symptom. Match the transform to the failure you observe, not to the newest paper.

Routing: pick the destination

Everything so far reshaped one query against one index. Real systems have many destinations — a code index and a prose index, a SQL database and a vector store, a fact-lookup prompt and a how-to prompt. Routing is the move that, before retrieving, decides where the query should go. It is the dispatcher standing in front of the retrieve loop, picking which corpus, which retriever, or which prompt template gets the query.

The simplest kind is logical routing: ask the language model to classify the query against a fixed set of named destinations, and dispatch on its answer. "Is this a question about Python, about SQL, or about our internal docs?" — the model returns a label, and you route to the matching index. It is a function-calling or classification step, deterministic in its branching once the label is chosen, and easy to audit because the destinations are an explicit, human-written list.

Logical routing shines when the destinations are discrete and well-named — distinct data sources, distinct schemas, distinct tools. You are leaning on the model's world knowledge to read intent (this mentions a SELECT, it wants the SQL tool) and map it onto a category you defined. The branches can be arbitrarily different downstream: one route hits a vector store, another writes SQL, a third calls an external API. The router only has to name the branch.

The contrast comes next beat with semantic routing, which drops the explicit labels and routes by embedding similarity to a set of destination prototypes — useful when the boundaries between destinations are fuzzy rather than categorical. Logical routing asks the model to name the bucket; semantic routing measures which prototype the query is nearest to. Same goal, two different mechanisms, suited to two different shapes of destination set.

Routing earns its place because it makes the whole pipeline modular. Instead of one monolithic index that must answer everything, you maintain several focused indexes and a thin router on top — each index stays clean and specialised, and the router absorbs the messy job of figuring out which one a given question belongs to. It is the retrieve arrow's traffic control: decide the destination first, then run the loop you already know.

Semantic routing, by hand

Semantic routing drops the named labels and routes by similarity to a prototype. Build one representative centroid vector per destination — typically by embedding that destination's prompt template, or averaging a few example queries that belong there — then route an incoming query to whichever centroid it is most cosine-similar to. The destination is chosen by \(\arg\max\) over similarities, no classifier call needed.

Work it on three destinations on three toy dimensions — factual-lookup, how-to/procedure, comparison. Their centroids are \(\texttt{factQA} = (3, 1, 1)\), \(\texttt{howTo} = (1, 3, 1)\), \(\texttt{compare} = (1, 1, 3)\): each leans hard on its own dimension. An incoming query embeds to \(q = (2, 3, 1)\) — moderate on factual, strong on procedure, light on comparison. Which centroid is it nearest to?

With \(\lVert q \rVert = \sqrt{14}\) and every centroid at norm \(\sqrt{11}\), cosine reduces to comparing the dot products. \(q \cdot \texttt{factQA} = 6 + 3 + 1 = 10\); \(q \cdot \texttt{howTo} = 2 + 9 + 1 = 12\); \(q \cdot \texttt{compare} = 2 + 3 + 3 = 8\). So \(\cos(q, \texttt{howTo}) = \dfrac{12}{\sqrt{14}\,\sqrt{11}}\) is the largest of the three, ahead of \(\dfrac{10}{\sqrt{14}\,\sqrt{11}}\) for factQA and \(\dfrac{8}{\sqrt{14}\,\sqrt{11}}\) for compare. \(\arg\max \Rightarrow\) route to howTo.

Because all three centroids happen to share the norm \(\sqrt{11}\), the cosine ranking is decided purely by the dot products \(12 > 10 > 8\) — the query's strong procedure component (the \(3\) in slot two) lines up with howTo's strong second slot, and that alignment dominates. The query goes to the how-to prompt and its how-to index, and the rest of the RAG loop runs exactly as before, just pointed at the right destination.

Semantic routing is the right tool when destinations blend into each other and a hard label would be arbitrary — "reset my password" and "how do I change my settings?" both lean procedural without naming a category. Logical routing names the bucket with the model's judgement; semantic routing lets geometry pick the nearest prototype. The deeper idea is that the same cosine you used to retrieve documents can route queries — routing is just retrieval over a tiny index of destinations.

Logical vs semantic routing

Two routers, one decision. Lay them side by side and the choice between logical and semantic routing comes down to the shape of your destination set — categorical or continuous — not to which is more sophisticated.

Logical routing — the model classifies the query into one of a named, fixed list of destinations and you dispatch on the label. Mechanism: an LLM classification or function call. Best when: destinations are discrete and well-named — a SQL tool versus a vector store, a Python index versus a docs index. Strengths: auditable (the label is explicit and human-readable), and the branches can be wildly different downstream. Weakness: you must enumerate the destinations up front, and a query that fits none gets force-fit into the nearest label.

Semantic routing — embed the query, embed a prototype per destination, route by \(\arg\max\) cosine. Mechanism: vector similarity, no generation. Best when: destination boundaries are fuzzy or numerous — many overlapping topic areas, prompt templates that shade into each other. Strengths: cheap (one embedding, no LLM call at route time) and graceful when destinations are similar (it picks the nearest, not a hard category). Weakness: the route is only as good as the prototypes, and a genuinely novel query still gets pulled to the nearest existing prototype.

The axes that separate them are cost and boundary type. Logical routing pays an LLM call but reasons about intent in natural language; semantic routing pays only a cosine but reasons only about geometric nearness. If your destinations are a short list of clearly distinct tools, the model's judgement (logical) is usually crisper. If they are a large or blurry set of topics, geometry (semantic) scales better and degrades more gracefully.

In practice they layer. A common arrangement is a coarse logical route first — database, or knowledge base? — and a fine semantic route within the knowledge base to pick the nearest topical sub-index. And note the unifying idea once more: semantic routing is retrieval over destinations, so everything you learned about embeddings and cosine transfers directly. Routing is not a new mechanism; it is the retrieve loop pointed at a tiny index whose documents are the destinations themselves.

Query construction: NL to structure

Routing chooses which store the query goes to. But some of those stores are not vector indexes at all — they are relational databases, document stores with metadata, graph databases. A bare embedding cannot query them; you need a structured query in their language. Query construction is the move that turns a natural-language question into the structured query a non-vector store actually understands.

The cleanest case is the self-query, also called metadata filtering. Many vector stores attach metadata to each chunk — topic, author, year, source — and let you combine a vector search with a structured filter. Self-query has the model read the natural-language request and emit both: the semantic part stays a vector search, and the constraints become a filter. "papers on retrieval published after 2020" becomes a vector search on retrieval plus a structured filter \(\{\texttt{topic}: \texttt{retrieval},\ \texttt{year}: \{\$gt: 2020\}\}\) — the model has separated the meaning (match by embedding) from the constraint (match by exact field).

The further case is text-to-SQL: the entire question maps to an executable query over a structured store. "how many documents did we index last month?" is not a semantic-similarity question at all — it is a count over a table, answered by \(\texttt{SELECT COUNT(*) FROM documents WHERE indexed\_at} \geq \dots\). Embeddings are useless here; the answer lives in rows, and the right retrieval is a database query the model writes from the natural-language request.

Query construction sharpens what "retrieve" can even mean. So far retrieval has been find the nearest vectors; construction adds find the rows that satisfy these exact constraints. Vector search excels at fuzzy semantic matching and is hopeless at precise filters ("exactly the 2023 papers"); structured queries are exact and hopeless at fuzzy meaning. A serious RAG system uses both — the model decides which part of the request is semantic and which is a hard constraint, and constructs the query accordingly.

The risk is real and worth naming: a model writing SQL or filters can write wrong ones — a hallucinated column name, a misread constraint, an injection-shaped string. Construction therefore wants guardrails: constrained generation against the known schema, validation before execution, read-only credentials. The payoff is a retriever that answers precise, structured questions the vector index simply cannot — but only if the constructed query is itself trustworthy.

Re-ranking the shortlist

The query is now well-aimed, well-routed, and broad enough to have recall. But the order of the retrieved shortlist still came from a fast, approximate scorer — the bi-encoder whose dot product you can compute over millions of chunks cheaply. Fast scorers trade accuracy for speed, so the true best passage often sits at rank \(4\), not rank \(1\). Re-ranking fixes the order: take the cheap retriever's top-\(k\) and re-score just those \(k\) with a slow, accurate model.

This is the cascade from Lecture 10, applied inside the RAG loop. The first stage — the bi-encoder — embeds query and chunks separately, so chunk vectors precompute and a query is one dot product away from a ranking over the whole corpus: fast, but the query and chunk never interact during scoring. The second stage — a cross-encoder — feeds the query and one candidate chunk together through a transformer, letting every query token attend to every chunk token. That joint attention is far more accurate and far too expensive to run over the corpus — so you run it only on the shortlist.

The economics are the whole point. A cross-encoder over a million chunks is hopeless; a cross-encoder over the bi-encoder's top \(20\) is trivial. So the bi-encoder buys recall cheaply across the corpus, and the cross-encoder buys precision expensively across the shortlist — each model doing the job it is efficient at. The re-ranker never has to see a chunk the retriever did not surface, which is exactly why recall upstream still matters: re-ranking can only reorder what retrieval already found. And the cross-encoder is itself a fallible model — on hard or adversarial pairs it can demote the right doc, and it adds \(k\) forward-pass latency — so the gate is recall AND re-ranker quality, not re-ranking alone.

Re-ranking sits at the stuff boundary of the loop, between retrieve and augment: get a shortlist, reorder it by the accurate scorer, then keep the top few for the token budget. Because the budget is tight (the lost-in-the-middle beat), order matters as much as membership — the cross-encoder's job is to make sure the chunk that actually answers the question lands at the top of what you stuff, not buried in the middle where the generator skims it.

The next beat puts numbers on the lift: a bi-encoder shortlist with the true doc at rank \(4\), re-scored by a cross-encoder that lifts it to rank \(1\), and the ranking metrics from Lecture 5 — nDCG and MRR — measuring exactly how much that reorder is worth. The frontier techniques after it (CRAG, Self-RAG) go one step further: instead of just reordering the retrieved set, they judge whether it should be used at all.

Re-ranking, by the numbers

Let me measure the re-rank with the graded-relevance metrics from Lecture 5, so the lift is a number rather than a hand-wave. Five candidates carry graded gains: \(d_2\) is the answer with gain \(3\), \(d_4\) is partially relevant with gain \(1\), and \(d_1, d_3, d_5\) are irrelevant with gain \(0\). The bi-encoder orders them \([d_1, d_3, d_4, d_2, d_5]\) — the answer \(d_2\) is buried at rank \(4\). The cross-encoder re-scores the same five and returns \([d_2, d_4, d_1, d_3, d_5]\) — the answer is now first.

Recall the metric: \(\mathrm{DCG} = \sum_i \frac{\text{gain}_i}{\log_2(\text{rank}_i + 1)}\), and \(\mathrm{nDCG} = \mathrm{DCG}/\mathrm{IDCG}\), where IDCG is the DCG of the ideal ordering. The ideal puts \(d_2\) (gain \(3\)) first and \(d_4\) (gain \(1\)) second: \(\mathrm{IDCG} = \frac{3}{\log_2 2} + \frac{1}{\log_2 3} = 3 + \frac{1}{\log_2 3}\).

Before (bi-encoder). Only \(d_4\) (gain \(1\), rank \(3\)) and \(d_2\) (gain \(3\), rank \(4\)) contribute: \(\mathrm{DCG} = \frac{1}{\log_2 4} + \frac{3}{\log_2 5} = \frac{1}{2} + \frac{3}{\log_2 5}\). Dividing by IDCG gives \(\mathrm{nDCG@5}\) just under one-half — the answer's burial at rank \(4\) costs most of the achievable score. The first relevant doc is at rank \(3\), so reciprocal rank \(\mathrm{MRR} = 1/3\). After (cross-encoder). \(d_2\) (gain \(3\)) sits at rank \(1\) and \(d_4\) (gain \(1\)) at rank \(2\) — the ideal order itself — so \(\mathrm{DCG} = \mathrm{IDCG}\) and \(\mathrm{nDCG@5} = \mathbf{1.0}\); the first relevant doc is rank \(1\), so \(\mathrm{MRR} = 1\).

So the reorder moved nDCG@5 from just under a half to a perfect \(1.0\), and MRR from \(1/3\) to \(1\) — and it did so without retrieving a single new document. The cross-encoder saw exactly the five chunks the bi-encoder surfaced; all it changed was their order, lifting the gain-\(3\) answer from rank \(4\) to rank \(1\). The gain came entirely from precision-in-the-ordering, which is the only thing a re-ranker controls.

Two lessons the numbers make sharp. First, re-ranking is bounded by recall: had the bi-encoder dropped \(d_2\) from the top-\(5\) entirely, no reorder could recover it, and the cross-encoder would be polishing a shortlist that no longer contains the answer. Second, the metric reflects where the answer lands, not merely whether it is present — and with a tight token budget that places only the top few chunks into the prompt, moving the answer from rank \(4\) to rank \(1\) is the difference between the generator reading it and skimming past it.

CRAG: grade the retrieval

Re-ranking reorders the shortlist but still trusts it. What if the retrieval is bad — the corpus simply does not contain the answer, or what it returned is off-topic? Stuffing it anyway invites the catch this lecture ends on: garbage in, fluent garbage out. Corrective RAG (CRAG; Yan, Gu, Zhu & Ling, arXiv:2401.15884, 2024) adds a checkpoint between retrieve and generate — a lightweight evaluator that grades the retrieval before the generator ever sees it.

The evaluator scores each retrieval and sorts it into one of three grades. Correct — the evaluator's confidence is high (say, above an upper threshold around \(0.7\)): the retrieved context is good, so use it as-is. Ambiguous — confidence is middling (between a lower and upper threshold): the context is partially useful but thin, so augment it with a corrective web search and combine the two. Wrong — confidence is low (below a lower threshold around \(0.3\)): the context is off-base, so discard it and fall back to web search or a query rewrite rather than ground on noise.

The thresholds here are illustrative, not measured — the point is the three-way branch, not the exact cutoffs. What matters is that CRAG turns retrieval from an unconditional input into a graded one: a confidence on the retrieval gates which of three actions the pipeline takes. Good retrieval flows straight through; thin retrieval gets reinforced; bad retrieval gets thrown out before it can poison the answer.

That third branch is the load-bearing one. A plain RAG loop has no way to say "I don't have good evidence for this" — it grounds on whatever came back, however irrelevant. CRAG gives it an off-ramp: when the corpus fails, reach outside it (web search) or re-ask (rewrite) instead of confidently summarising noise. The corrective step is precisely the missing defense against the catch beat's failure mode — it inspects \(R\) before the generator commits to it.

CRAG is the first member of the self-correcting family: the loop no longer trusts its own retrieval blindly but evaluates and repairs it. The next beat, Self-RAG, internalises this judgement into the model itself rather than bolting on a separate evaluator — and after that, Adaptive-RAG asks whether to retrieve at all. Each adds a layer of self-awareness to a loop that, until now, has marched straight through retrieve-augment-generate without ever questioning the middle.

Self-RAG: the model critiques itself

CRAG bolted a separate evaluator onto the loop. Self-RAG (Asai, Wu, Wang, Sil & Hajishirzi, ICLR 2024, arXiv:2310.11511) moves the judgement inside the model: it trains the language model to emit special reflection tokens as it generates, so the same model that writes the answer also decides when to retrieve and critiques what it retrieved. The control logic is no longer an external wrapper — it is woven into the generation itself.

Four reflection tokens carry the self-awareness. Retrieve — emitted before a segment, it decides whether retrieval is even needed here: a segment the model already knows skips retrieval entirely; one that needs grounding triggers it. IsRel — after retrieving, it asks is this passage actually relevant?, filtering the retrieved context the model itself just pulled. IsSup — as it writes, it asks is this claim supported by the passage?, checking that each generated statement is grounded rather than invented. IsUse — at the end, it rates is the overall response useful? on a small scale, a final quality gate on the whole answer.

The crucial token is the first. A plain RAG loop retrieves unconditionally — every query triggers a retrieval, even "what is two plus two?" where the model needs no corpus and retrieval only adds noise and latency. Self-RAG's Retrieve token lets the model retrieve on demand, segment by segment: ground the parts that need grounding, answer the rest from its own parameters. Retrieval becomes a decision the model makes, not a reflex the pipeline forces.

The other three tokens turn faithfulness into something the model self-reports as it goes. IsRel is CRAG's relevance grade, but emitted by the generator itself; IsSup is a running citation-faithfulness check on each claim; IsUse is a final usefulness score. Together they make the model an inline critic of its own output, flagging unsupported claims and irrelevant context during generation rather than after. Crucially, the model is trained to emit these — they are learned behaviour, not a prompt-engineering trick layered on at inference.

Self-RAG is the self-correcting idea taken to its limit: not a checkpoint around the model, but self-critique within it. It anticipates exactly the question the lecture closes on — is the answer faithful to its sources? — by having the model grade its own support as it writes. But notice the loop it creates: the model is now judging itself, and a model that grades its own faithfulness can also learn to game its own grade — the trap the next lecture, judging the Oracle, has to confront head-on.

Adaptive-RAG: retrieve only when needed

Self-RAG let the model choose to retrieve per segment. Adaptive-RAG (Jeong, Baek, Cho, Hwang & Park, NAACL 2024, arXiv:2403.14403) raises that decision to the whole query and makes it a deliberate first step: a small query-complexity classifier reads the incoming question and routes it down one of three paths of escalating cost. Not every question deserves the same machinery, and matching effort to difficulty is the whole idea.

Three tiers. No retrieval — for a simple question the model already knows the answer to ("what is the capital of France?"), skip the corpus entirely; retrieval would only add latency and noise. Single-step RAG — for a question that needs one fact from the corpus ("what does our refund policy say about returns after 30 days?"), do exactly one retrieve-augment-generate pass, the loop you have built all lecture. Multi-step RAG — for a complex, multi-hop question ("compare how the policy changed between the 2022 and 2024 handbooks and explain why"), run an iterative loop: retrieve, reason, retrieve again, until the question is fully answered.

This is routing applied to effort rather than destination. Logical and semantic routing chose which index a query hits; Adaptive-RAG chooses how much pipeline a query deserves. The classifier is the dispatcher, and the cost of an answer now scales with the difficulty of the question instead of being flat — a one-fact lookup no longer pays the price of a multi-hop investigation, and a multi-hop investigation is no longer starved by a single-pass budget.

The economics are why this matters at scale. Retrieval has real cost — latency, compute, and the dilution that an unnecessary context injection adds — so retrieving for a question the model could answer from its parameters is pure waste, and answering a multi-hop question with a single pass is pure failure. Adaptive-RAG spends retrieval where it pays and skips it where it does not, which is exactly the discipline the budget and lost-in-the-middle beats argued for, now automated by a classifier instead of a fixed policy.

Place the three self-correcting techniques together and a hierarchy of self-awareness appears. CRAG asks was the retrieval good? (grade it, repair it). Self-RAG asks should I retrieve here, and is each claim supported? (in-line, learned). Adaptive-RAG asks how hard is this question? (route by complexity). The loop that began the lecture as a fixed retrieve-augment-generate has grown a brain about its own behaviour — and that growing self-judgement is exactly the thread the next lecture, judging the Oracle, picks up.

Anatomy of the generation prompt

Every technique so far sharpened retrieve and augment. The last arrow, generate, is where the retrieved context becomes an answer — and its quality hinges almost entirely on how the prompt is assembled. The prompt is not a free-form blob; it has an anatomy, and each part does a specific job in turning chunks into a grounded, cited answer.

Three parts, in order. The system instruction sets the contract: "Answer the question using ONLY the provided context. If the context does not contain the answer, say you don't know. Cite the source of each claim." This single instruction is what separates RAG from a bare LLM — it forbids the model from falling back on parametric memory and demands citations. The context block is the retrieved chunks, concatenated, each tagged with a source id so the model can cite it. The question comes last, after the context, because models attend strongly to the end of a prompt — you want the actual ask fresh in view when generation begins.

Order inside the context block is not cosmetic. The lost-in-the-middle effect means the model reads the start and end of a long context most reliably, so you place the highest-ranked chunks at the edges and let the weaker ones fill the middle — which is exactly why the re-ranker's job (get the best chunk to rank \(1\)) feeds directly into prompt assembly. A perfectly retrieved chunk dumped into the dead middle of a long context can still be skimmed past.

The instruction also encodes the failure behaviour you want. "If the context does not contain the answer, say you don't know" is the single most important line in a RAG prompt, because it is the model's permission to abstain rather than fabricate. Without it, a model handed thin or irrelevant context will helpfully invent an answer — the exact catch this lecture ends on. The prompt is where you tell the Oracle that "I couldn't find that" is an acceptable, even preferred, answer when the evidence is not there.

And citation formatting lives here too: instruct the model to attach the source id to each claim — "...ejects blood [doc_cardiac_cycle]." — so the answer is verifiable. That is the contract from the loop's first beat made operational: answer using only what was retrieved, and say where each claim came from. Retrieval found the evidence; the generation prompt is the discipline that turns it into a grounded, attributable answer rather than a fluent guess.

The seven-strategy map

Step all the way back. This lecture introduced a whole zoo of RAG techniques, and they are easy to confuse precisely because they all sit on the same loop. The way to keep them straight is to ask of each: which arrow of retrieve-augment-generate does it sharpen? Seven families, mapped to the loop, organise the entire lecture.

Chunking acts before the loop — it decides what the elements \(c_i\) are (fixed, recursive, semantic, late). Indexing also acts before retrieval — multi-representation and RAPTOR decide what handle each chunk gets indexed under. Query translation sharpens the query going into retrieve — multi-query, RAG-Fusion, HyDE, decomposition, step-back, all editing \(q\). Routing sits at the front of retrieve — logical and semantic, choosing the destination. Query construction changes the kind of retrieval — NL into a metadata filter or SQL.

Re-ranking acts after retrieve, before stuff — the cheap-then-accurate cascade reordering the shortlist. Self-correction wraps the whole loop in judgement — CRAG grades the retrieval, Self-RAG critiques inline, Adaptive-RAG routes by complexity. Read the seven in loop order — chunk, index, translate, route, construct, re-rank, self-correct — and you have walked the pipeline from corpus to grounded answer, with every technique slotted into the arrow it improves.

Two things fall out of the map. First, the techniques compose rather than compete: a serious system chunks recursively, indexes with summaries, routes the query, translates it with multi-query plus fusion, re-ranks the shortlist, and self-corrects the result — they stack along the loop because each touches a different arrow. Second, almost none of them touch the generator: the bulk of RAG engineering is upstream retrieval work, which is the lecture's deepest lesson — a great answer is mostly a great retrieval, presented well.

And notice what anchors the whole map: every arrow is still bounded by the recall floor from the loop's formal beat. Chunking decides what is findable; query translation and routing decide what is aimed at; re-ranking and self-correction decide what is trusted — but if the answer was never retrieved, no downstream cleverness recovers it. The seven strategies are seven ways to push more signal through the same loop; the loop's discipline is unchanged.

When to reach for what

Seven strategy families is a lot of machinery, and the worst way to use them is to bolt on every technique at once. The discipline is the opposite: start with the simplest loop that works, measure where it fails, and reach for the specific technique that fixes that symptom. Match the tool to the failure you can observe, not to the newest paper you read.

Read the symptoms. "The answer exists but isn't retrieved." That is a recall failure — reach for query translation (multi-query, HyDE) to widen and re-aim, or revisit chunking so the answer is carved into a findable unit. "It's retrieved but ranked too low to make the budget." That is an ordering failure — reach for re-ranking to lift the right chunk to the top. "Answers about recent events are wrong or refused." The corpus is stale or thin — reach for CRAG's web-search fallback.

Keep reading. "Multi-part questions get half-answered." Reach for decomposition. "The query has to hit a database or a metadata filter." Reach for query construction. "We're paying for retrieval on questions that don't need it." Reach for Adaptive-RAG to route by complexity. "Broad and narrow questions both have to work against one corpus." Reach for RAPTOR's multi-level tree. Each symptom names a slot in the loop, and the slot names the technique.

Two cautions keep the toolbox honest. First, complexity has a cost: every added stage is more latency, more LLM calls, more places to fail and debug — so add a technique only once you have measured the failure it fixes, and remove it if the measurement does not improve. Second, almost everything here is retrieval engineering, not generation: the generator is largely fixed, and the leverage is in feeding it better context — which is why this whole lecture lived upstream of the generate arrow.

And every one of these levers raises the same final question. Whether you widened recall, re-ranked, decomposed, or self-corrected, you still produced a fluent, confident, cited answer — and you still cannot tell from the outside whether it is true. That is the wall this lecture deliberately stops at, and the next one starts at: how do you grade an Oracle whose every answer sounds right? The applicability map tells you which lever to pull; it cannot tell you whether the answer it produced is faithful.

Garbage in, fluent garbage out

RAG has a sharp failure mode, and the poisoned pipeline above shows it: if retrieve brings back wrong or irrelevant passages, augment stuffs them in, and generate dutifully writes a fluent, confident answer grounded in garbage. The recall floor strikes again — the generator can only be as good as what retrieval brought back.

Here is Confabulous, the hallucination phantom, in its first appearance: it hands the Oracle a forged citation, and the Oracle recites it with the same assurance as a true one. Confident and correct look identical from the outside — which is precisely the problem the next lecture must solve. How do you grade an Oracle?

Two ways to be wrong

The poisoned pipeline showed one way an Oracle fails — bad retrieval feeding a fluent answer. But pull the failure apart and there are really two distinct questions about any grounded answer, and they come apart in ways that matter. An answer can be relevant to the question yet unfaithful to its sources, or faithful to its sources yet irrelevant to what was asked.

Relevance asks: does the answer address the question? It is about the question-answer relationship — did the Oracle actually respond to what was asked, or did it drift onto a neighbouring topic? Faithfulness asks a separate thing: is every claim in the answer supported by the retrieved context? It is about the answer-source relationship — is the Oracle reading the chunks, or embroidering beyond them? The two are orthogonal, and you need both.

See how they dissociate. An answer can be perfectly relevant — it directly addresses "how does the heart pump blood?" — while quietly slipping in a claim no retrieved chunk supports (a confident hallucination dressed as a citation: relevant, unfaithful). Or an answer can be scrupulously faithful — every sentence traceable to a chunk — while answering a different question than the one asked, because retrieval handed it on-topic-but-not-on-question passages (faithful, irrelevant). Either way the answer reads fine; only the two-axis test catches the gap.

Confabulous, the phantom from the catch beat, is the personification of the unfaithful failure: it hands the Oracle a forged citation, and the Oracle recites it relevantly and confidently, faithful only to a source that was never real. From the outside — the fluent prose, the citation marker, the assured tone — a faithful answer and an unfaithful one are indistinguishable. That indistinguishability is the entire problem, and no retrieval technique in this lecture detects it: every lever we pulled improved what reached the generator, none of them checked what the generator did with it.

Which is exactly where this lecture has to stop. We built an Oracle that retrieves well and speaks fluently — but speaking well is not speaking truly, and we have no instrument yet to tell them apart. Measuring relevance and faithfulness — putting numbers on whether an answer is grounded and on-target, and confronting a judge that can itself be gamed — is the work of the next lecture. Here we only need to know the two axes exist; there we learn to score them.

The Oracle speaks

End to end, the Oracle speaks: chunk the corpus, embed and retrieve through the lanes, stuff the best passages into the budget, and generate an answer grounded in them, with citations. The whole pipeline lights green — fast, fluent, sourced. The Ship no longer merely finds; it answers.

But is it telling the truth? A confident answer and a correct one look identical, and Confabulous proved a fluent lie costs nothing. Grounded looking is not grounded being.
