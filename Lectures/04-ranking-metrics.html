This is my proving grounds — the place where every system gets tested before it earns my trust. I'm at the scoreboard comparing two ships' runs. The whole spine of this course is Measure, and without an honest measure of ranking quality every later claim I make is hot air. This part is me showing you why a single number is unavoidable.

You can't eyeball quality at scale

why we need a number

Reading one ranking by eye is fine. Judging \(10^{4}\) queries by eye is not — and "looks good" cannot be averaged, compared, or trended over time. We need three things: a relevance label per result (ground truth), a metric that turns a ranking into one comparable score, and statistics to tell signal from noise.

The core problem. With one query you can skim the list and form an opinion. But a real evaluation set has thousands of queries, and opinions don't aggregate: you cannot average "looks good", you cannot tell whether yesterday's change helped, and you cannot compare two systems fairly. The fix is a number — but a number needs ground truth to compare against, and a difference between two numbers needs a significance test before you believe it. Labels, metric, statistics: that is the spine of the lecture.

Two regimes: offline and online

the lecture roadmap

This is the map for the whole day. Offline evaluation uses a frozen test collection: a set of queries with human labels, so you can score any system instantly and repeatably — perfect for the inner loop of development. But labels are a proxy. Online evaluation puts the change in front of real users and measures behaviour, which is the real thing you care about — but it is slow, noisy, biased by position, and risky. Part 02

Relevance
judgments

Before I can score a ranking, I need to know which results are actually correct — so first I appoint the referee.

✓ You can now justify why one number is unavoidable. Next: where the ground truth comes from.

Every offline metric I compute compares the system's ranking against a set of relevance judgments — qrels. My referee decides, for each (query, document) pair, whether it is relevant. Without this ground truth I have nothing to measure against. This part is where that ground truth comes from and how much I should trust it.

Key term

Definition
Definition
Relevance judgmentsqrels

A relevance label attached to each (query, document) pair: is this document a correct answer for this query?

Ours are binary and come for free from the corpus: a document is relevant if it shares the query's 20 Newsgroups category. The running query has intent space, so relevant means category sci.space — the same labels-as-truth convention we used in Lectures 1–3.

Qrels are the answer key. In a production system humans annotate them; here we reuse the 20 Newsgroups category labels as ground truth, so a document about space (category sci.space) is relevant to a space query and anything else is not. Binary relevance for the counting metrics; we add graded relevance later for nDCG. This continuity with L1–L3 is deliberate: we grade the very catalog we already built.

Binary vs graded relevance

two label scales

Binary · \(\{0,1\}\)

Relevant or not. Simple, cheap, fast to annotate. Feeds the counting metrics: \(\mathrm{P}@k\), \(\mathrm{R}@k\), MRR, MAP.

i
Our running labels

Pattern \([0,1,0,1,0,1,0,1]\) over the BM25 top-8: \(4\) relevant docs at ranks \(2,4,6,8\).

Graded · TREC \(0\)–\(4\)

Degrees of relevance: a perfect hit beats a marginal one. Required for nDCG, which weights by graded gain.

i
Our graded labels

Grades \(0/1/3\): off-topic \(=0\), marginally relevant \(=1\), strong space hits \(=3\). In rank order: \([0,3,0,3,0,1,0,1]\).

Grading rule (so the grades aren't invented): a doc squarely on the query topic — a focused sci.space article — scores \(3\); one that only touches it in passing (mentions a launch inside an off-topic post) scores \(1\); anything off-topic scores \(0\). Same rubric TREC assessors use, scaled to three levels.

Binary throws away "how relevant". Graded keeps it — and a rank-1 perfect hit should out-score a rank-1 marginal one. Part 04 is built on the graded scale.

The label scale decides which metrics you can even compute. Binary is yes/no — cheap and the foundation of the counting family. Graded — TREC uses 0 through 4, we use 0/1/3 — captures that some relevant docs are far better than others, which is exactly what nDCG needs. We carry both scales for the same running ranking, so you'll see the very same eight documents scored binary in Part 3 and graded in Part 4.

The cost wall

!
You cannot judge everything

\(N\) docs \(\times\) \(|Q|\) queries explodes. A 1M-doc corpus with 50 queries = 50M pairs — impossible to label exhaustively.

So we judge only a sample of documents per query. Which sample? That is the pooling problem on the next slide.

Judgments are expensive human labour. A guideline document pins down what the query means and what counts as relevant, so different assessors agree. The fundamental problem is scale: you cannot label every document for every query — the product is astronomical. Real corpora are judged on a sample, and the sampling strategy matters enormously, because a metric only sees the docs that were judged. That sets up pooling.

Pooling & the Cranfield / TREC paradigm

how test collections are built
Method
Poolingdepth-\(k\) pool

Run many systems on each query; take the top \(k\) from each; union them into a pool; have assessors judge only the pool.

The Cranfield paradigm (1960s) established reusable test collections (judged near-exhaustively); pooling arrived in the 1970s as a sampling technique and TREC (1992–) industrialised it: a reusable test collection = queries + pooled qrels. A document outside every system's top-\(k\) is assumed non-relevant — usually safe, because relevant docs tend to surface near the top of some system.

Cranfield in the 1960s established the recipe that still rules: fixed queries, fixed documents, fixed relevance judgments, so any system can be scored offline and compared — Cranfield itself judged near-exhaustively. The trick that makes large collections affordable is pooling, introduced as a sampling technique in the 1970s: instead of judging all documents, you pool the top-k of every participating system and judge only that union. TREC industrialised it from 1992. The bet is that any genuinely relevant document is found by at least one decent system and lands in the pool. Voorhees showed pooled collections are robust enough to reuse for years.

Common misconception

the unjudged-document problem
What people assume

“If a document wasn't judged relevant, it's safe to count it as non-relevant.”

Only safe inside the pool. A new system can retrieve genuinely relevant docs that no pooled system found — these are unjudged, and "unjudged = non-relevant" unfairly penalises it. The deeper your retrieval differs from the pool, the worse the bias.

The fix. Use measures robust to incomplete judgments: bpref (counts only judged docs) or condensed-list metrics (delete unjudged docs, then score). They evaluate on judged evidence only, so an innovative ranker isn't punished for finding relevant docs the pool missed.

This is the subtle trap of reusing a test collection. Within the pool, "unjudged = non-relevant" is fine. But a brand-new system — say, a dense retriever that ranks documents nobody pooled — surfaces relevant docs that were never judged, and the standard convention scores them as wrong. The system gets punished precisely for being different and good. bpref and condensed-list metrics restrict scoring to judged documents, removing the penalty. Buckley and Voorhees introduced bpref for exactly this reason.

Do the judges even agree?

Cohen's \(\kappa\) · label noise
$$ \kappa = \frac{p_o - p_e}{1 - p_e} $$
\(p_o\)
Observed
fraction of pairs the two judges label the same
\(p_e\)
Chance
agreement expected from label rates alone
\(\kappa\)
Agreement
\(1\) perfect, \(0\) chance, \(<0\) worse

Rule of thumb: \(\kappa>0.6\) substantial, \(>0.8\) near-gold. Many judges → Fleiss' \(\kappa\). Low \(\kappa\) means your "ground truth" is noisy and caps the metric's resolution.

Ground truth is not handed down from heaven — humans disagree, especially on borderline relevance. Cohen's kappa corrects raw agreement for the agreement you'd get by chance: subtract chance, normalise by the room left above chance. Above 0.6 is usually called substantial, above 0.8 near-gold; Fleiss generalises to more than two judges. The practical lesson: if your annotators only weakly agree, your labels are noisy, and no metric can resolve system differences finer than that noise. Measure agreement before you trust the qrels.

Quick check

Audience question
A new dense retriever returns relevant docs that no pooled system ever surfaced. Scored with plain \(\mathrm{P}@k\) on the old qrels, what happens?
AIt is unfairly penalised — its unjudged-but-relevant hits count as non-relevant.
BNothing — pooled qrels are always complete.
CIt scores artificially high because new docs default to relevant.
Reveal explanation
A. The pool was built from the old systems' top-\(k\); a document none of them retrieved is unjudged, and the "unjudged = non-relevant" convention marks the new system's genuine finds as misses. This is the reusability limit of pooled collections — use bpref or condensed metrics to evaluate fairly.
Consolidates Part 2. The point: a test collection is only as reusable as its pool is complete relative to the system you're testing. If your new system retrieves in a genuinely different way, its best documents may be invisible to the qrels and you'll under-credit it. The defensive move is to know your pool depth and prefer robust measures when evaluating off-pool systems.

Counting
metrics

✓ You can now collect judgments and read their agreement. Next: turn them into a score.

With my ground truth fixed, I can count. These metrics all treat relevance as yes/no. Precision and Recall answer "how clean / how much" at a cutoff; F combines them; MRR asks "how soon the first hit"; MAP rolls precision over every hit into one number. I compute them all on the running ranking — and MRR and MAP get a second query so you see the averaging actually do something.

Precision & Recall: the confusion-matrix roots

retrieved vs relevant

Build the grid from scratch: cross did we return it? (yes/no) with is it actually relevant? (yes/no), and the four cells are TP (returned & relevant), FP (returned, not relevant), FN (relevant, not returned), TN (correctly left out).

$$ \mathrm{Precision} = \frac{\mathrm{TP}}{\mathrm{TP}+\mathrm{FP}} = \frac{\text{relevant retrieved}}{\text{retrieved}}, \qquad \mathrm{Recall} = \frac{\mathrm{TP}}{\mathrm{TP}+\mathrm{FN}} = \frac{\text{relevant retrieved}}{\text{relevant}} $$

In ranking we apply these at a cutoff \(k\) — "retrieved" = the top \(k\) — giving \(\mathrm{Precision}@k\) and \(\mathrm{Recall}@k\).

Precision and recall are not IR inventions — they are the confusion matrix from classification, read through a retrieval lens. Precision is "of what I returned, how much was right"; recall is "of all the right answers, how many did I return". In ranking there is no single "returned" set, so we impose a cutoff k: the top k is the retrieved set. That turns both into functions of k, which is where the real story begins on the next slide.

\(\mathrm{Precision}@k\) and \(\mathrm{Recall}@k\)

how clean vs how much, at a cutoff \(k\)
$$ \mathrm{Precision}@k = \frac{\#\{\text{rel in top }k\}}{k}, \qquad \mathrm{Recall}@k = \frac{\#\{\text{rel in top }k\}}{\#\{\text{rel total}\}} $$
\(k\)

\(\mathrm{Precision}@k\)

\(\mathrm{Recall}@k\)

Same numerator, different denominator: \(\mathrm{Precision}@k\) divides by \(k\), \(\mathrm{Recall}@k\) divides by total relevant.

Two sides of the same coin. Both count how many relevant docs sit in the top k; they differ only in what they divide by. Recall measures coverage — of everything relevant, how much did we surface — and rises monotonically toward 1 as k grows. Precision measures purity — of what we showed, how much was good — and tends to fall as k grows because you scrape further down. The precision–recall tradeoff & \(F_1\)

one curve, one summary number

The four points are plotted to scale — \(@1\,(0,0)\), \(@3\,(0.25,0.333)\), \(@5\,(0.5,0.4)\), \(@8\,(1.0,0.5)\) — and the curve runs through them. (On this particular ranking the hits cluster at even ranks, so precision actually rises with \(k\); the textbook curve usually falls.) \(F_1=\dfrac{2PR}{P+R}\) is their harmonic mean — punishing imbalance — and the 11-point interpolated curve and \(F_\beta\) (\(\beta>1\) favours recall) generalise it.

Precision and recall pull against each other, and the PR curve draws that tension: every cutoff is one operating point. F1 collapses the two into one number using the harmonic mean, which — unlike the arithmetic mean — refuses to be fooled by a system that maxes one and tanks the other. F-beta tilts the balance: beta above 1 weights recall more, useful when missing a relevant doc is costlier than showing a bad one. The 11-point interpolated precision is the classic smoothing TREC used to average PR curves across queries.

R-precision: a self-scaling cutoff

when "k" should depend on the query
Definition
R-precision\(\mathrm{P}@R\)

Precision at cutoff \(k=R\), where \(R\) is the number of relevant documents for that query. At \(k=R\), precision and recall coincide.

Our query has \(R=4\), so R-precision \(=\mathrm{P}@4\). Top-4 contains relevant docs at ranks \(2,4\) → \(2/4 = 0.5\). It auto-adapts: a query with 100 relevant docs is judged at \(k=100\), not a fixed 10.

A fixed cutoff like P@10 is unfair across queries: a query with three relevant docs can never exceed 0.3, while one with fifty is judged on a tiny window. R-precision fixes this by setting the cutoff to R, the number of relevant docs for that query. A neat property falls out: at k = R, precision equals recall, because the denominators k and R are the same. For our query R = 4, so it's P@4 = 0.5. It's a single, query-adaptive number that correlates strongly with MAP in practice.

Mean Average Precision (MAP)

precision, sampled at every hit · \(\approx\) area under PR
$$ \mathrm{AP} = \frac{1}{R}\sum_{k\,:\,\mathrm{rel}_k=1} \mathrm{Precision}@k, \qquad \mathrm{MAP} = \frac{1}{|Q|}\sum_{q\in Q}\mathrm{AP}(q) $$
\(R\)

\(\mathrm{AP}\)

AP looks at every rank where a relevant doc appears, so it rewards ranking relevant docs higher. GMAP uses the geometric mean — emphasising hard queries.

MAP is the workhorse of binary-relevance IR. Average Precision evaluates Precision@k at each rank where a relevant document actually sits, then averages those values over the number of relevant docs — which is, to a good approximation, the area under the precision-recall curve. Because precision is higher when hits are near the top, AP rewards surfacing relevant docs early. MAP is AP averaged over queries arithmetically; GMAP uses the geometric mean, which weights improvements on already-hard queries more heavily. My counting metrics treat every relevant doc as equally good and only loosely reward position. nDCG fixes both: it uses graded gains (some docs are more relevant than others) and a smooth logarithmic position discount, then normalises by the best possible ordering so the score lands in [0, 1] and is comparable across queries. This is the headline metric of modern web ranking, and the one I'll lean on hardest.

Why graded relevance & position matter

two things counting metrics miss

Not all hits are equal

A perfect, on-topic, authoritative result is worth more than a barely-relevant one. Binary relevance flattens this; graded gain keeps it.

i
Our grades \(0/1/3\)

Strong space hits (D3, D2) \(=3\); marginal (D0, D1) \(=1\); hockey \(=0\).

Rank 1 \(\gg\) rank 8

Users read top-down and rarely scroll. A relevant doc at rank 1 helps far more than the same doc at rank 8 — so the metric must discount by position.

i
The discount

Each rank \(i\) is divided by \(\log_2(i+1)\): rank 2 keeps \(0.63\), rank 8 only \(0.32\).

nDCG exists because the counting family ignores two facts. First, relevance is graded: an authoritative, exactly-on-topic document beats a tangential one, and we lose that with 0/1 labels. Second, position is everything: people scan from the top and almost never reach rank 8, so a hit there is nearly worthless compared to a hit at rank 1. nDCG bakes both in — graded gain in the numerator, a position discount that shrinks with depth. Adjacent graded metrics: ERR & RBP

two explicit user models — the intuition, not the algebra

ERR · the user who stops

A cascade: the user reads top-down and quits the moment a result satisfies them. So one great hit at rank 1 makes everything below it almost worthless. ERR is essentially a graded MRR — reward for satisfying the user early.

i
When to reach for it

Single-answer / known-item search, where the user leaves as soon as they're happy. Chapelle et al., 2009.

RBP · the user who persists

The user steps to the next rank with a fixed probability \(p\) and stops otherwise — so attention decays geometrically down the list. Tune \(p\) to model a patient (\(p\to1\)) vs impatient (\(p\to0\)) user; the discount is a knob, not a fixed log.

i
When to reach for it

Browsing tasks where you want to encode how far users actually scroll. Moffat & Zobel, 2008.

Both swap nDCG's fixed log discount for an explicit user model. You don't need the algebra; for reference: \(\mathrm{ERR}=\sum_r \tfrac{1}{r}R_r\!\prod_{i \lt r}(1-R_i)\) and \(\mathrm{RBP}=(1-p)\sum_r g_r\,p^{\,r-1}\), with stop-prob \(R_r\propto 2^{\mathrm{rel}_r}-1\).

Two metrics worth knowing because they encode an explicit user model, unlike nDCG's fixed log discount. Expected Reciprocal Rank assumes a cascade: the user reads down the list and stops as soon as a document satisfies them, so a great result early makes everything below it nearly irrelevant — it's a graded, cascade-aware cousin of MRR. Rank-Biased Precision assumes a persistent user who continues to the next rank with probability p; tune p to model patient versus impatient users. You don't need the algebra memorised — I've left it as a one-line reference at the foot of the slide — but know they exist and why a user model can beat a fixed discount.

Power: how many queries do you need?

minimum detectable difference

The four knobs

  • ·Effect size — the true gap you want to catch (e.g. \(+0.01\) nDCG).
  • ·Variance — per-query spread (\(\mathrm{sd}=0.0676\) here).
  • ·\(\alpha\) — false-positive rate (usually \(0.05\)).
  • ·Power \(1-\beta\) — chance of catching a real effect (aim \(0.8\)).

The consequence

!
Small effects need many queries

To reliably detect a \(+0.01\) nDCG gain at this variance, you need hundreds of queries, not 15. Under-powered tests miss real wins (Type II).

\(n \approx \left(\dfrac{(z_\alpha + z_\beta)\,\mathrm{sd}}{\text{MDD}}\right)^2\). Halve the detectable difference → quadruple the queries.

Significance and power are two failure modes. Significance controls false positives — saying B won when it didn't. Power controls false negatives — missing a real win because the test was too small. The required query count grows with variance and shrinks with the effect you're willing to call meaningful; crucially, it scales with the inverse square of the minimum detectable difference, so chasing a tiny improvement costs a lot of queries. Fifteen queries can catch a 0.04 gap but would routinely miss a real 0.01 gap. Decide the smallest gain you care about before you size the test.

Common misconception

the multiple-comparisons trap
What teams do

“We tried 20 variants, one hit \(p<0.05\) — that one's a real winner.”

At \(\alpha=0.05\), 1 in 20 random tests is "significant" by chance. Test 20 variants and you expect one false positive even if none is truly better. Cherry-picking the winning p-value is how teams ship noise.

The fix. Correct for the number of comparisons: Bonferroni (test at \(\alpha/m\)) or Benjamini–Hochberg (control the false-discovery rate). Better still: pre-register one hypothesis, or confirm the winner on a fresh query set / an online A/B test.

This is the most common statistical sin in applied ranking work. A p-value below 0.05 means a 5% chance of a false alarm per test. Run twenty tests and the expected number of false alarms is one — so the "winner" you cherry-picked may be pure noise. Bonferroni divides alpha by the number of tests (conservative); Benjamini-Hochberg controls the false-discovery rate (more powerful). The cleanest defence is to confirm an offline winner on held-out queries or, better, in an online experiment — which is exactly where Part 6 takes us.

A/B testing: guardrails & pitfalls

how A/B tests lie

Guardrail metrics

  • ·CTR up but latency up, or revenue down? Watch guardrails, not just the target.
  • ·CTR can rise from clickbait — pair it with dwell / conversion.

Three classic traps

!
Peeking · novelty · seasonality

Peeking: checking \(p\) repeatedly inflates false positives — fix \(n\) up front or use sequential tests. Novelty: users click anything new at first. Seasonality: run full weeks, not Tuesday afternoons.

An A/B test answers "did behaviour change", not "did the ranking get better" — guardrails and a clean design keep the two aligned.

A/B tests are powerful but easy to fool. Guardrail metrics catch a treatment that wins on the target while quietly hurting something else — latency, revenue, long-term retention. CTR especially can be gamed by clickbait, so always pair it with a satisfaction signal like dwell time or conversion. Three procedural traps: peeking at the p-value repeatedly is the online cousin of multiple comparisons and inflates false positives — commit to a sample size or use a sequential test; novelty effects make anything new look good for a few days; and seasonality means you must run full weekly cycles. Design first, then run.

Clicks are biased by position

examination probability · the examination (position-based) model

Geometric examination model: \(P(\text{exam}\mid \text{rank}) = \gamma^{\,\text{rank}-1}\) with \(\gamma=0.94\). A doc at rank 1 is examined with prob \(1.0\); at rank 10 only \(0.57\). A click means "relevant and examined" — so low ranks get fewer clicks regardless of quality.

The single biggest reason raw clicks lie. Users examine the top of the list far more than the bottom, so a click conflates two things: was the result relevant, and was it even looked at. The examination (position-based) model formalises this — examination depends only on rank; here we use a geometric form, probability of examining rank r is gamma to the r minus 1, gamma 0.94. Rank 1 is examined with certainty, rank 10 only 57% of the time. So a great result buried at rank 8 earns few clicks not because it's bad but because nobody saw it. Any click-based metric must correct for this. One caveat: this examination model is the simplest of a family. The cascade model (Craswell et al. 2008) makes examination of rank r conditional on not being satisfied by anything above it, so the ranks couple — a strong rank-1 result starves the clicks below it (the same intuition ERR uses on slide 36). And a click also needs the snippet to be attractive: caption/trust bias means users sometimes click on the wording, not the true relevance. So debiasing position alone is incomplete.

overview
Interleaving is the sharpest tool in online evaluation. Instead of showing A to one group and B to another, you blend both rankers into a single list the user sees — team-draft alternates picks like captains choosing a team, tagging each slot with its source. Every click credits the ranker that placed that result. Because both rankers compete within the same list for the same user, position bias largely cancels: each occupies high and low slots equally often. Each round both teams pick, so the slots split evenly; B wins on the clicks. Over five queries A earns 9 credits, B earns 16, preference for B is 16/25 = 0.64, B preferred in four of five queries. Joachims showed interleaving needs far less traffic than A/B to reach the same confidence. Two caveats. First, you don't declare a winner from the bare 0.64 — you run a binomial/sign test on the per-query preferences (the per-query pairing is exactly why interleaving is more sensitive than A/B at equal traffic). Second, team-draft can mis-credit documents the two rankings share, and it has a known tie bias; probabilistic and optimised interleaving (Radlinski & Craswell; Chapelle et al. 2012, already cited on slide 60) fix these.

Inverse Propensity Scoring: clicks are biased by what the old policy chose to show. Divide each reward by its propensity → an unbiased estimate of a new policy's value from logged data. Foundation of unbiased learning-to-rank. Two catches: small \(p_i\) make \(r_i/p_i\) explode (high variance — cap/clip or use self-normalised IPS), and every evaluable item needs \(p_i>0\) (support), or the estimate is biased, not just noisy.

The most modern idea here. Logged clicks are biased twice over — by position (slide 51) and by the logging policy itself, which only ever showed certain documents. Inverse Propensity Scoring corrects this: weight each observed reward by one over the probability that the old policy displayed it, so items the old system rarely showed but a user still clicked get up-weighted. The result is an unbiased estimate of how a new policy would have performed, computed entirely from logs without running a fresh experiment. Joachims and colleagues built unbiased learning-to-rank on exactly this — train and evaluate rankers from biased click logs. It needs accurate propensities, which is the hard part. Two failure modes beyond that. Variance: a rarely-shown item has a tiny propensity, so r over p explodes — the estimator stays unbiased but can be uselessly noisy. The standard fixes are clipping/capping the propensities or self-normalised IPS (SNIPS), which divides by the sum of weights. And support (positivity): every action you want to evaluate must have had p greater than zero in the logs, or IPS is biased, not merely noisy, because some outcomes are never observed.

Does offline predict online?

sometimes — and when it doesn't, offline lies

Across many launches, offline nDCG gains usually correlate with online CTR gains — but not always. The red point is the dangerous case: a change that improved the offline metric and hurt users. Offline is a filter, not a verdict.

The empirical question that ties the lecture together. If offline metrics perfectly predicted online outcomes, we'd never need experiments — but they don't, only correlate. Most of the time a real offline nDCG gain shows up as an online click or conversion gain, which is why offline iteration works at all. The red outlier is the trap: a change that games the offline metric — maybe by exploiting label quirks or the unjudged-document bias — looks like an improvement offline yet degrades the real user experience. That's Goodhart, which is exactly where Part 7 goes. Validate offline winners online before you trust them.

Common misconception

What teams think

“If we optimise the metric, the system must be getting better.”

Goodhart's law: when a measure becomes a target, it stops being a good measure. Optimise a proxy (clicks, popularity) and the ranking can look busier while genuine relevance falls. The metric you trained on quietly stops measuring what you cared about.

Worked example — binary-gain nDCG. Relevance is binary (4 sci.space docs), so all use the same ideal:
\(\mathrm{IDCG} = 1.0 + 0.6309 + 0.5 + 0.4307 = 2.5616\).
Gamed order [D6,D7,D5,D4,D3,D2,D0,D1] buries the 4 relevant docs at ranks 5–8:
\(\mathrm{DCG} = 0.3869 + 0.3562 + 0.3333 + 0.3155 = 1.3919 \Rightarrow \mathrm{nDCG} = 1.3919/2.5616 = 0.5434\).
Honest BM25 order: \(\mathrm{DCG} = 0.6309 + 0.4307 + 0.3562 + 0.3155 = 1.7333 \Rightarrow 1.7333/2.5616 = 0.6766\).

Gaming in practice

where Goodhart bites for real

Adversaries & artifacts

  • ·SEO spam — keyword-stuffing games lexical relevance signals.
  • ·Clickbait — maximises CTR while tanking dwell & trust.
  • ·Feedback loops — train on biased clicks → reinforce position bias → train on it again.

Defences

  • ·Held-out human judgments the optimiser never sees.
  • ·Guardrail + satisfaction metrics, not just the target.
  • ·Debias clicks (IPS) before training on them.
  • ·Confirm offline wins with an online A/B / interleaving test.

Every metric in this lecture is a proxy. The discipline is to keep one honest signal the optimiser can't touch.

Goodhart isn't abstract; it's the daily reality of running a search engine. SEO spam games lexical signals; clickbait games CTR; and the nastiest case is the feedback loop — you train a ranker on click logs, which are biased toward whatever the old ranker showed at the top, so the model learns to reinforce position bias rather than relevance, and the next round of logs is even more biased. The defences echo the whole lecture: keep held-out judgments the optimiser never sees, watch guardrails and satisfaction not just the target, debias clicks with IPS before learning from them, and always confirm an offline win online. One honest, untouchable signal is what keeps the rest from rotting.
