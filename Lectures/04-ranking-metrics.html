Part 01

The Proving
Grounds

Two search systems. Which one is better? "Looks good to me" is not an answer.

The proving grounds: the place where every system is tested before it earns trust. Serega stands at a scoreboard comparing two ships' runs. The whole spine of this course is Measure — and without an honest measure of ranking quality, every later claim is hot air. This part motivates why a single number is unavoidable.

You can't eyeball quality at scale

why we need a number

Reading one ranking by eye is fine. Judging \(10^{4}\) queries by eye is not — and "looks good" cannot be averaged, compared, or trended over time. We need two things: a relevance label per result (ground truth), and a metric that turns a ranking into one comparable score.

The core problem. With one query you can skim the list and form an opinion. But a real evaluation set has thousands of queries, and opinions don't aggregate: you cannot average "looks good", you cannot tell whether yesterday's change helped, and you cannot compare two systems fairly. The fix is a number — but a number needs ground truth to compare against. That ground truth is the next part.
Part 02

Relevance
judgments

Before you can score a ranking, you need to know which results are actually correct.

Every metric in this lecture compares the system's ranking against a set of relevance judgments — qrels. The referee decides, for each (query, document) pair, whether it is relevant. Without this ground truth there is nothing to measure against.

Key term

Definition
Definition
Relevance judgmentsqrels

A relevance label attached to each (query, document) pair: is this document a correct answer for this query?

Ours are binary and come for free from the corpus: a document is relevant if it shares the query's 20 Newsgroups category. The running query has intent space, so relevant means category sci.space — the same labels-as-truth convention we used in Lectures 1–3.

Qrels are the answer key. In a production system humans annotate them; here we reuse the 20 Newsgroups category labels as ground truth, so a document about space (category sci.space) is relevant to a space query and anything else is not. Binary relevance for the counting metrics; we add graded relevance later for nDCG. This continuity with L1–L3 is deliberate: we grade the very catalog we already built.

query intent: space · relevant = sci.space

Part 03

Counting
metrics

Binary relevance, four lenses: \(\mathrm{Recall}@k\), \(\mathrm{Precision}@k\), MRR, MAP.

With ground truth fixed, we can count. These four metrics all treat relevance as yes/no. Recall and Precision answer "how much / how clean at a cutoff"; MRR asks "how soon the first hit"; MAP rolls precision over every hit into one number. All computed on the running ranking.

\(\mathrm{Recall}@k\) and \(\mathrm{Precision}@k\)

how much vs how clean, at a cutoff \(k\)
$$ \mathrm{Recall}@k = \frac{\#\{\text{relevant in top }k\}}{\#\{\text{relevant total}\}}, \qquad \mathrm{Precision}@k = \frac{\#\{\text{relevant in top }k\}}{k} $$
\(k\)
Cutoff
how far down the list we look
\(\mathrm{Recall}@k\)
Coverage
fraction of all relevant docs found by rank \(k\)
\(\mathrm{Precision}@k\)
Purity
fraction of the top \(k\) that is relevant

Same numerator, different denominator: \(\mathrm{Recall}@k\) divides by total relevant, \(\mathrm{Precision}@k\) divides by \(k\).

Two sides of the same coin. Both count how many relevant docs sit in the top k; they differ only in what they divide by. Recall measures coverage — of everything relevant, how much did we surface — and rises monotonically toward 1 as k grows. Precision measures purity — of what we showed, how much was good — and tends to fall as k grows because you scrape further down. Next slide walks the exact values.

Walk it one row at a time, reading numerator/denominator aloud. Recall marches 0 → 0.25 → 0.5 → 1.0: by rank 8 we have found all four relevant docs. The two metrics disagree on purpose; that disagreement is exactly why we report both at chosen cutoffs.

Mean Reciprocal Rank (MRR)

how soon does the first hit arrive?
$$ \mathrm{MRR} = \frac{1}{|Q|}\sum_{q\in Q} \frac{1}{\mathrm{rank}_1(q)} $$
\(\mathrm{rank}_1(q)\)
First hit
rank of the first relevant doc for query \(q\)
\(\tfrac{1}{\mathrm{rank}_1}\)
Reciprocal rank
\(1\) if first, \(0.5\) if second, \(\ldots\)
\(|Q|\)
Query count
average over the query set

Our query: first relevant doc is at rank \(2\), so \(\mathrm{RR}=1/2=0.5\). With one query, \(\mathrm{MRR}=\mathrm{RR}=0.5\).

MRR cares about one thing only: how far you must scroll before the first correct answer. The reciprocal makes rank 1 worth 1.0, rank 2 worth 0.5, rank 10 worth 0.1 — it rewards getting something right immediately and ignores everything after the first hit. Perfect for "I need one good answer fast" tasks like question answering. For our ranking the first relevant doc (D3) is at rank 2, giving reciprocal rank 0.5; averaging over a single query leaves MRR at 0.5.

Mean Average Precision (MAP)

precision, sampled at every hit
$$ \mathrm{AP} = \frac{1}{R}\sum_{k\,:\,\mathrm{rel}_k=1} \mathrm{Precision}@k, \qquad \mathrm{MAP} = \frac{1}{|Q|}\sum_{q\in Q}\mathrm{AP}(q) $$
\(R\)
Relevant total
here \(R=4\)
\(\mathrm{rel}_k=1\)
Hit ranks
sum \(\mathrm{Precision}@k\) only where a relevant doc lands
\(\mathrm{AP}\)
Average precision
one number per query; MAP averages it

Unlike \(\mathrm{Precision}@k\), MAP looks at every rank where a relevant doc appears, so it rewards ranking relevant docs higher.

MAP is the workhorse of binary-relevance IR. Average Precision evaluates \(\mathrm{Precision}@k\) at each rank where a relevant document actually sits, then averages those values over the number of relevant docs. Because precision is higher when hits are near the top, AP rewards a system that surfaces relevant docs early. MAP is just AP averaged over all queries. \(\mathrm{AP} = \dfrac{0.5+0.5+0.5+0.5}{4} = 0.5\); with one query, \(\mathrm{MAP}=0.5\). Every hit lands one rank below a non-relevant doc, so each precision is exactly \(0.5\).

The relevant docs sit at ranks 2, 4, 6, 8 — each immediately after a non-relevant doc — so \(\mathrm{Precision}@k\) at every hit is exactly one-half. Averaging four halves over the four relevant docs gives AP = 0.5, and MAP = 0.5 for this single query. The uniform 0.5 is a tidy artifact of the perfectly alternating pattern; on real query sets these values vary and MAP separates good systems from bad.
Part 04

Graded relevance:
nDCG

Not all hits are equal, and a hit at rank 1 beats a hit at rank 8.

Counting metrics treat every relevant doc as equally good and only loosely reward position. nDCG fixes both: it uses graded gains (some docs are more relevant than others) and a smooth logarithmic position discount, then normalizes by the best possible ordering so the score lands in [0, 1] and is comparable across queries.

DCG, IDCG, and nDCG

gain, discounted by position, then normalized
$$ \mathrm{DCG}@k = \sum_{i=1}^{k} \frac{g_i}{\log_2(i+1)}, \qquad \mathrm{nDCG}@k = \frac{\mathrm{DCG}@k}{\mathrm{IDCG}@k} $$
\(g_i\)
Gain
graded relevance of the doc at rank \(i\)
\(\log_2(i+1)\)
Discount
deeper ranks are worth less
\(\mathrm{IDCG}@k\)
Ideal DCG
DCG of the best possible ordering

Dividing by \(\mathrm{IDCG}@k\) (the gain you'd get sorting docs best-first) puts \(\mathrm{nDCG}\) in \([0,1]\): \(1\) is a perfect ranking.

Three pieces. DCG sums each doc's gain divided by a logarithmic position discount, so a relevant doc high up contributes more than the same doc buried deep. IDCG is the DCG of the ideal ranking — all the highest-gain docs first — which is the maximum achievable. Dividing DCG by IDCG normalizes to [0, 1], making nDCG comparable across queries with different numbers of relevant docs. Next slide walks the discount column on our ranking.

The headline computation, all exact. Discounts: \(1/\log_2 3=0.6309\), \(1/\log_2 5=0.4307\), \(1/\log_2 7=0.3562\), \(1/\log_2 9=0.3155\). Only relevant ranks contribute, so \(\mathrm{DCG}=0.6309+0.4307+0.3562+0.3155=1.7333\). The ideal ranking puts all four relevant docs at ranks 1–4, giving \(\mathrm{IDCG}=1/\log_2 2+1/\log_2 3+1/\log_2 4+1/\log_2 5=2.5616\). The ratio is \(\mathrm{nDCG}=1.7333/2.5616\approx 0.677\) — a single number you can compare to any other ranker on this query.

Why nDCG < 1: the ideal ladder

DCG vs IDCG

The ideal ranking front-loads all relevant docs (ranks \(1\)–\(4\)) for \(\mathrm{IDCG}=2.5616\); our BM25 ranking scatters them to ranks \(2,4,6,8\) for \(\mathrm{DCG}=1.7333\). Their ratio, \(\mathrm{nDCG}\approx 0.677\), says we captured about two-thirds of the achievable gain.

The intuition behind normalization. IDCG is the score of a perfect ranker that puts every relevant doc as high as possible; it is the ceiling for this query. Our ranker scattered the relevant docs down the list, paying the log discount each time, so it earns only 1.7333 of the available 2.5616 — about 68%. nDCG = 0.677 is therefore "two-thirds of the way to perfect", a phrase you can compare directly against any other system on the same query set.

Common misconception

Goodhart the Trickster
What teams think

“If we optimise the metric, the system must be getting better.”

Goodhart's law: when a measure becomes a target, it stops being a good measure. Optimise a proxy (clicks, popularity) and the ranking can look busier while genuine relevance falls. The metric you trained on quietly stops measuring what you cared about.

Worked example. Take a "popularity-first" ranking that pushes a popular-but-off-topic doc to the top: order [D6, D7, D5, D4, D3, D2, D0, D1].
It looks active and clickable, but every relevant doc is now below the irrelevant ones.
Result: \(\mathrm{nDCG}=0.543\) versus our honest BM25 ranking's \(0.677\). The popularity hack scores lower, not higher.

Goodhart the Trickster returns — first met in Lecture 1, now in his home territory of Measure. The trap: teams chase an easy proxy like click-through or popularity, assuming it tracks relevance. It does not. The gamed ranking here stuffs popular hockey docs at the top; it looks engaging but pushes every space doc downward, so nDCG drops from 0.677 to 0.543. The lesson: a metric is only honest while it is not the thing being gamed — which is exactly why we evaluate against held-out relevance judgments, not against the signal we optimised.
