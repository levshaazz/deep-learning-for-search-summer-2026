Part 01

The Star Catalog

I'm a star-cartographer now — one record in a billion, and I cannot read them all at query time.

I'm a star-cartographer now. The sky is my corpus; each star is a document. A user asks me for one specific star out of a billion — and I cannot visit each one and check. My answer is the search engineer's answer: build a catalog indexed by what you are looking for, so a query lands you on the right page instantly.

The retrieval problem

query → which of \(N\) documents?

Retrieval = given a query, return the small relevant subset out of \(N\). The relevant set is a handful; the corpus is billions. The whole game is finding the handful without inspecting the billions.

State the task cleanly. A query names a tiny relevant subset hidden in an enormous corpus. The naive approach scores every document and keeps the best — correct, but unaffordable. The art of classical IR is to reach the relevant handful while looking at as few documents as possible, which is exactly what an inverted index buys.

Scanning every document is hopeless

Obstacle · brute force does not scale

A linear scan costs \(O(N)\) per query. At \(N\approx 10^{9}\) and ~1 µs per touch that is ~1000 s — about 17 minutes per query, against a ~100 ms budget. Off by four orders of magnitude.

The arithmetic kills brute force. A billion documents at a microsecond each — one µs is a realistic figure for a single in-cache comparison — is roughly a thousand seconds, about seventeen minutes, per query. The budget is about a hundred milliseconds. You are off by four orders of magnitude, and no faster CPU saves you, because the cost grows linearly with the corpus. The only way out is to not look at most documents at all, which is exactly what an index buys.

Where the ~100 ms budget comes from

attention · QPS · fan-out
  • ·Human attention. Past ~100 ms a UI feels sluggish; past ~1 s users abandon. Search must feel instant.
  • ·Throughput (QPS). A big engine serves tens of thousands of queries per second; per-query cost is multiplied by that rate.
  • ·Fan-out. One query hits hundreds of index shards in parallel; the slowest shard sets the latency, so each must finish in a few ms.
i
The budget is a hard wall

A retrieval stage gets only a slice of ~100 ms; the rest goes to re-ranking, snippet generation, and the network. So first-stage retrieval must be sublinear in the corpus size.

This is why we precompute a structure once and consult it per query, instead of scanning documents.

The budget is not arbitrary. It is set by human perception (a sluggish UI loses users), by throughput (cost is paid tens of thousands of times per second), and by fan-out (a query is split across many shards and the slowest one wins). Within that hundred-millisecond wall, first-stage retrieval gets only a slice — so it has to be sublinear in N. That requirement is the whole motivation for the inverted index.

The move

precompute once, don't scan per query
Key idea
Index, don't loopoffline build · online lookup

Pay an offline cost once to build a data structure, so that each online query is a few cheap lookups instead of a full \(O(N)\) scan.

The structure is the inverted index: for every term, the list of documents that contain it. A query term becomes a dictionary lookup; the candidate set shrinks from a billion to a few thousand before any scoring happens.

The conceptual pivot of Part 1. The corpus is mostly static; queries are endless. So move all the heavy work to build time and make query time trivial. The inverted index is precisely that trade: build it once, consult it forever. After this slide, every later idea — compression, skip pointers, BM25 scoring — is an optimisation on top of this structure.
Part 02

The Inverted Index

I've proved brute force is hopeless — now I flip the map: instead of doc → words, store word → which docs.

My reveal. A normal document maps doc to its words. My catalog flips it: for every term, I store the list of documents that contain it — a postings list, one catalogue card per word. Now a query term is a single lookup, not a scan. This is the inverted index, the foundation of every full-text search engine for fifty years. The image is my card-wall metaphor; the text stands alone if it 404s.

A map from each term to its postings list — the documents (and often positions / counts) in which that term appears.

"Inverted" because it reverses the natural document → terms map into a terms → documents map. A query term becomes a single dictionary lookup; boolean queries become merges of postings lists. This is the data structure behind Lucene, Elasticsearch, and every classical engine.

Index construction at scale

BSBI · SPIMI · sort + merge · segments

The problem

The full term–doc pair list doesn't fit in RAM. Both classic algorithms build blocks in memory, then merge on disk.

  • ·BSBI (blocked sort-based): collect (termID, docID) pairs, sort each block, write to disk, then external-merge.
  • ·SPIMI (single-pass in-memory): grow per-term postings directly, no global sort; flush a block when memory fills.

In production

i
Lucene segments

New documents form small immutable segments; background merges combine them into larger ones. Writes are append-only; deletes are tombstones.

This is how Elasticsearch / Solr index continuously without rebuilding the whole index.

Construction must be out-of-core because the pair list dwarfs RAM. BSBI sorts blocks of termID-docID pairs and external-merges them; SPIMI skips the global sort by accumulating postings per term and flushing when memory runs out — simpler and faster in practice. Real engines layer on segments: every flush is an immutable segment, and a background merge policy keeps the segment count bounded, which is what makes near-real-time indexing possible.

Bag-of-Words &
the Vector Space Model

Before I can rank, I have to turn a document into something a machine can weigh — a vector of counts.

Before I can build any scorer I need a representation. The simplest one that works is the Bag-of-Words: I throw away order and keep counts. Stack those count vectors and I get the document-term matrix; treat each row as a point in term space and I have the vector space model. Naming these explicitly fixes a gap the old deck had — TF-IDF and BM25 are weightings on top of this representation.

Key term

Definition
Definition
Bag-of-WordsBoW

Represent a document by the multiset of its words — keep how often each term appears, discard the order.

A document becomes a vector indexed by the vocabulary: entry \(i\) is the count of term \(i\). Stack the vectors for all documents and you get the document-term matrix. It is the input to TF-IDF, BM25, and classic text classifiers.

Name it. The Bag-of-Words model is the single most important representation in classical IR: a document is just a vector of word counts over a fixed vocabulary. The word "bag" is literal — order is thrown away, only multiplicity survives. Every weighting we study (raw counts, TF-IDF, BM25) is a transformation of this count vector. Its great virtue is simplicity; its great flaw, that it forgets word order, comes two slides on.

Live BoW: a spam filter

word counts → spam / ham

A classic BoW application: features are word counts, and Naïve Bayes multiplies per-word likelihoods \(P(\text{word}\mid\text{class})\). "free", "money", "winner" push toward spam; order never matters. Same representation, different task than retrieval.

Concrete BoW in the wild. A spam filter ignores grammar entirely: it counts words and asks which class makes those counts more likely. Naïve Bayes assumes words are independent given the class and multiplies their likelihoods — crude, but famously effective on email. The point for us is that the very same Bag-of-Words vector that feeds a classifier here feeds a retrieval scorer in the rest of the lecture. The representation is shared; only the downstream model changes.

Two structural limits. First, discarding order means "dog bites man" and "man bites dog" have identical representations — fatal for tasks where word order carries meaning, partially patched by n-gram features. Second, the vectors live in a space with one dimension per vocabulary word, so they are enormous and almost entirely zero; we never materialise them densely, we store the inverted index. And crucially, distinct strings are orthogonal axes, so synonyms get no credit — the lexical gap, which we name properly in Part 8.

Vector Space ModelVSM · Salton 1975

Represent both documents and queries as vectors in the same term space, and rank documents by their geometric closeness to the query vector.

A query is just a very short document. Relevance becomes a distance / angle, so retrieval reduces to "find the document vectors nearest the query vector" — the bridge from counts to a real ranking.

Salton's vector space model is the conceptual leap that makes ranking possible. Once documents and the query live in the same term space, "relevant" becomes "close", and we can sort by similarity. The query is treated as a tiny document. This reframing is what lets us replace yes/no boolean matching with a continuous score — and it is exactly the geometry we measured with cosine in Lecture 2, now put to work for retrieval.

Why raw counts fail → motivate TF and IDF

frequent words drown the signal

Rank by raw count and every document is "about" the. We need two corrections: TF (a sublinear take on within-document frequency) and IDF (down-weight terms common across the corpus). That is TF-IDF, next.

Motivate the whole of Part 4. If you score documents by raw word counts, the winner is always dominated by stopwords like "the" and "of" — they are frequent everywhere and informative nowhere. Two fixes are needed and they are orthogonal: damp the within-document term frequency so repetition has diminishing value, and down-weight terms that appear in many documents because ubiquity means low specificity. Those are TF and IDF, and their product is the first real ranking weight.

Intuition: a word that appears 10× is more relevant than once, but not 10× more. So every useful TF is sublinear in \(f\) — the seed of BM25's saturation.

Term frequency comes in flavours, all sharing one principle: more is better, but with diminishing returns. Raw count is linear and over-rewards repetition. Log-tf, one plus log f, is the classic sublinear choice. Augmented tf normalises by the document's max frequency to stop long documents from dominating. The takeaway is that good TF is sublinear in the count — which is precisely the property BM25 formalises with its saturation function. Hold that thread; it returns in Part 5.

Spärck Jones's insight: a term's value is its rarity. A word in every document (\(df=N\)) scores \(\log 1 = 0\); a word in one document scores \(\log N\) — it pinpoints.

Karen Spärck Jones, 1972: the weight of a term should reflect how specific it is, and specificity is rarity. Inverse document frequency is the log of the corpus size over the document frequency. A term that appears everywhere has idf zero and contributes nothing; a term in a single document has the maximum idf and is a near-perfect locator. This single idea is why search ignores stopwords without ever maintaining a stopword list — they simply earn zero weight.

The theoretical foundation. The Probabilistic Ranking Principle states that if you order documents by their probability of relevance to the query, you maximise the expected usefulness to the user — it is provably optimal under reasonable assumptions. The practical move is to rank by the odds of relevance rather than the probability directly, because the odds factorise into per-term contributions once you apply Bayes' rule and an independence assumption. That factorisation is what produces a sum over query terms, the shape every scorer in this part shares.

The Binary Independence Model represents a document as a set of present-or-absent terms and, under independence, the odds of relevance factorise into a sum of per-term weights. With no relevance judgments to estimate from, that weight reduces to the Robertson–Spärck-Jones form — the probabilistic relative of idf. Note the subtlety: the raw RSJ weight can go negative when a term sits in more than half the corpus (and on a tiny collection like cat/dog/mouse it would), so in practice — and in every worked example in this deck — we use the +1-clamped form from slide 32, ln(1 + (N−n+0.5)/(n+0.5)), which stays non-negative. This is BM1. Its limitation is glaring once stated: it only asks whether a term is present, never how many times — so it cannot tell a document that mentions "shuttle" once from one that is entirely about shuttles. Fixing that is the next step.

Why saturation: about t vs merely mentions t

the theoretical "why" — no probability prerequisite needed

A document is either about \(t\) (the topic recurs) or merely mentions it (in passing). The best weight that tells the two apart rises with tf but flattens — the principled origin of saturation. (Formally: model tf as a 2-Poisson mixture, one component per regime — the 2-Poisson model is Harter 1975; the eliteness/saturation reading of it is Robertson et al. 1981.)

This is the theory the old deck never gave: why saturation. Robertson's eliteness idea says each document is either elite for a term — genuinely about that concept, so the term recurs — or not, where it appears only incidentally. Model the term count as a mixture of two Poisson distributions, one per class — the 2-Poisson model itself goes back to Harter 1975 — and the optimal weight from the likelihood ratio is an increasing but bounded function of tf. In other words, the saturating shape is not an engineering hack; it falls out of a principled probabilistic model. BM25's tf factor is a cheap, robust approximation to that curve.

The engineering beat that gives BM25 its character. Across the Okapi TREC runs the authors learned three things. Diminishing returns on term frequency

TF-IDF is linear · BM25 saturates

From \(f=1\) to \(f=2\) adds a lot; from \(f=9\) to \(f=10\) almost nothing. TF-IDF climbs linearly forever; BM25 is concave toward \(k_1+1\). Smaller \(k_1\) saturates sooner — a whole family of curves.

A picture of saturation. TF-IDF is a straight line through the origin — the hundredth occurrence is worth the same as the first. BM25 is concave and bounded, rising steeply for the first few occurrences then flattening toward a ceiling proportional to k1 plus one. The parameter k1 selects a curve from a family: smaller k1 saturates sooner, larger k1 stays linear longer. This matches intuition — once a document is clearly about a topic, more repetitions tell you little — and it is the single most important difference between the two scorers.

The \(b\) dial: long vs short documents

\(b=0\) ignores length · \(b=1\) penalizes fully

At \(b=0\) a term's contribution is independent of length. As \(b\to1\), a document longer than average is penalized more and a shorter one boosted — all pivoting at \(\mathrm{len}=\mathrm{avgdl}\). The default \(0.75\) is a strong-but-not-total penalty.

The companion picture to saturation. Hold term frequency fixed and vary document length. At b zero the line is flat — length is irrelevant. As b rises toward one, documents longer than the average lose score and shorter ones gain, and all the lines pivot at exactly the average length, where the bracket equals one regardless of b. The default 0.75 is a deliberate three-quarters penalty: enough to stop long documents winning by sheer accumulation, not so much that a legitimately thorough long document is crushed.

PageRank

My sextant scores text, but not trust — so I ask a new question: which stars do other stars point to?

My BM25 scores how well a document's text matches a query, but it says nothing about how trustworthy or important the document is. PageRank, Page, Brin, Motwani & Winograd 1998, supplies the missing query-independent signal from the link graph: a page is important if important pages link to it. In my star metaphor, stars vote for each other along their links, and the most-endorsed star shines brightest regardless of any particular query.

A link is a vote — weighted by the voter

query-independent authority

Treat each inbound link as a vote for the target. But not all votes are equal: a link from an authoritative page is worth more. Authority is therefore recursive — you are important if important pages point to you.

The core intuition. The web's link structure encodes human judgment: linking to a page is an implicit endorsement. A naive count of inbound links is gameable and crude, so PageRank weights each vote by the importance of the voter — a single link from a highly authoritative site outweighs many links from obscure pages. That makes the definition recursive: your rank depends on the ranks of the pages linking to you, which depend on theirs. Resolving that recursion is what the power iteration does, two slides on.

A surfer follows a random link with prob \(d\), else teleports to a random page. Teleport makes the walk ergodic — it breaks out of cycles and guarantees one unique stationary rank. A true sink (a dangling page with no out-links) needs one more fix: redistribute its mass each step, or treat it as linking to all pages.

PageRank is the stationary distribution of a random surfer. With probability d, here 0.85, the surfer follows one of the current page's out-links uniformly; with probability one minus d it teleports to a uniformly random page. The teleport term is not cosmetic — without it a small cycle acts as a rank sink that absorbs all probability mass and never gives it back, so the iteration never converges to anything useful. Teleport guarantees the chain is ergodic, so a unique stationary distribution exists. A true dangling page with no out-links is a separate issue: damping alone does not conserve mass when one exists — its mass has to be reinjected each step (treat it as linking to every page, or renormalise). Our toy graph has no dangling node, so it sidesteps that. That stationary distribution is the rank.

Rank Fusion

I now hold three rankers that disagree — so I convene a council of navigators and combine their votes into one robust list.

My rankers see different things — BM25 reads exact terms, a cosine ranker reads direction in vector space, PageRank reads authority. Each produces its own ranked list on its own incomparable scale. Rather than trust one navigator, I convene a council: a document several navigators rank highly should rise. The robust, parameter-light way I fuse them is Reciprocal Rank Fusion, which I build up to through the whole fusion family.

Why fuse rankers at all

complementary strengths · incomparable scales

Each ranker has a blind spot

  • ·BM25 — great on exact / rare terms (names, IDs); blind to synonyms.
  • ·Dense cosine — bridges synonymy; weak on rare exact tokens.
  • ·PageRank — authority, but query-independent.
!
Scales don't match

BM25 scores are unbounded (\(0\) to \(\sim\)tens); cosine is \([-1,1]\); PageRank is a probability summing to 1. Adding them raw lets one ranker silently dominate.

Fusion exists because rankers are complementary and their scores are not. BM25 nails exact and rare terms but misses synonyms; a dense cosine ranker does the opposite; PageRank adds authority but ignores the query. So a document that one system misses, another often catches — fusing improves recall and robustness. The catch is that the scores live on wildly different scales: BM25 is unbounded, cosine sits in minus one to one, PageRank is a tiny probability. Naively summing them lets whichever has the biggest numbers win. The fusion family is a set of answers to that scale problem.

Hybrid search: the modern reason RRF matters

The production pattern

Run a sparse (BM25) and a dense (embedding) retriever in parallel, then RRF their two lists. Lexical exactness + semantic recall, no score calibration.

i
Why RRF here

BM25 and cosine scores are utterly incomparable; RRF needs neither calibrated, so it is the default in Elasticsearch, OpenSearch, Weaviate, and most RAG stacks.

When fusion fails

  • ·All rankers share the same blind spot → fusing adds nothing.
  • ·One ranker is far stronger → the weak ones add noise; weight or drop them.
  • ·Highly correlated lists → diversity, not redundancy, is what helps.
The reason RRF is everywhere today is hybrid search. The standard production retriever runs BM25 and a dense embedding model in parallel and fuses with RRF, getting lexical exactness and semantic recall in one list without ever calibrating the two score scales — which is why it ships as the default in Elasticsearch, OpenSearch, Weaviate, and most RAG pipelines. But fusion is not magic. If every ranker shares the same blind spot, fusing them just reproduces it. If one ranker dominates, the weak ones inject noise and should be down-weighted or dropped. Fusion pays off only when the rankers are genuinely diverse — they must disagree usefully.

BM25 matches exact terms, not meaning. A query for couch scores zero on a document that only says sofa — same concept, different string, no overlap. This is the lexical gap: classical IR is blind to synonyms, paraphrase, and spelling variants.

The Lexical Gremlin. It wedges a wall between couch and sofa so no postings list ever connects them. Stemming and query expansion patch a few cases, but the wall stands. My catch beat. I over-trusted BM25 too, because it works so well on exact terms. But it is a string matcher with clever weighting — it has no notion of meaning.
