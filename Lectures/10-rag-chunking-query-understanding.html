Part 1 · From finding to answering

The Oracle

The Ship has always found records. Today it learns to answer. A bare model is fluent — and sometimes confidently wrong. Ground it in what our lanes retrieved, and it reads before it speaks. Enter RAGdoll the Oracle.

Cold open. Callback to L9 (lanes open, retrieval fast) → but finding ≠ answering. RAGdoll the Oracle, the hero.

Confident ≠ correct

why a bare LLM can't be trusted as a search answer

Three failures

  • Stale — parametric memory froze at training time.
  • Unciteable — it cannot point to a source.
  • Confident either way — a correct answer and a fabricated one sound identical.

The fix: grounding

Not a bigger model — retrieval. Don't ask the model to know; make it read what we retrieved, then answer using only that, with citations. That is the RAG loop.

problem-ungrounded. Parametric staleness + no citation + confident hallucination. Grounding, not scale, is the fix.

"A bigger model won't hallucinate"

grounding, not scale — the lecture's thesis
What students think

“Just use a bigger model — hallucination is a capacity problem, and a larger model trained on more tokens will simply know the answer.”

Scale sharpens fluency, not provenance — a bigger model is a more convincing guesser, still confident when it is wrong. Parametric memory is frozen at training time and unciteable: a private, fresh, or proprietary corpus is something no pre-training can hold. The fix is orthogonal to size: retrieve the evidence and make the model read it. RAG adds non-parametric memory (the index) alongside the parametric model — Lewis et al., 2020.
why-grounding-not-scale. The thesis misconception: scale ≠ grounding. RAG = parametric + non-parametric memory (Lewis et al., NeurIPS 2020). Sets up the whole lecture.
Act 1 · The loop & the index

Retrieve → augment → generate

Don't ask the model to know — make it read. Retrieve the top passages through everything we built (index, embeddings, cascade, ANN lanes); stuff them into the prompt; generate an answer grounded in them. Retrieval sits upstream — RAG consumes it.

turn-rag. The three moves. Retrieval (L3–L9) is upstream; RAG doesn't replace it. Act 1 also covers how you INDEX (chunking, RAPTOR, Late Chunking).

RAG, formally

the loop as one equation
Definition · retrieval-augmented generation
$$ \text{answer} \;=\; G\big(q,\; R_k(q)\big), \qquad R_k(q) \;=\; \operatorname*{top\text{-}k}_{d \in \mathcal{C}} \; s\!\big(\mathbf{e}_q,\, \mathbf{e}_d\big) $$
  • ·\(R_k(q)\) — the retriever returns the k chunks of corpus \(\mathcal{C}\) scored highest by a scorer \(s\) (in our toy, \(s=\cos\)). This \(s\) is everything from L3–L9: BM25, bi-encoder, ColBERT MaxSim, cross-encoder cascade, ANN lanes.
  • ·\(G(\cdot)\) — the generator (an LLM) reads the query and the retrieved chunks, and writes an answer grounded in them, with citations.
  • ·The whole lecture is two questions about this equation: what goes into \(R_k\) (chunking, indexing, query translation, routing), and how to make \(R_k\) and \(G\) more reliable (re-rank, self-correction).
RAG-loop-formally. answer = G(q, R_k(q)); R_k = top-k by a general scorer s (toy: s = cosine). s is everything from L3–L9 (BM25/dense/ColBERT/cascade, retrieval upstream). G is the LLM. Frames the whole lecture: improve what feeds R_k, and make R_k + G reliable.

Where the retrieval scores come from

\(R_k\) is just cosine — by hand on the anchor trace
$$ \cos(\mathbf{e}_q,\mathbf{e}_d) = \frac{\mathbf{e}_q\cdot\mathbf{e}_d}{\lVert\mathbf{e}_q\rVert\,\lVert\mathbf{e}_d\rVert}, \qquad \mathbf{e}_q = (3,2,1,1) $$ $$ \text{cardiac cycle } (1,2,1,2):\ \frac{10}{\lVert\mathbf{e}_q\rVert\,\lVert\mathbf{e}_d\rVert} = \mathbf{0.8165} $$ $$ \text{circulatory } (1,2,2,2):\ \frac{11}{\lVert\mathbf{e}_q\rVert\,\lVert\mathbf{e}_d\rVert} = \mathbf{0.7877} \qquad \text{valves } (1,5,0,2):\ \frac{15}{\lVert\mathbf{e}_q\rVert\,\lVert\mathbf{e}_d\rVert} = \mathbf{0.7071} $$

The four dimensions are pump · anatomy · flow · valves. Higher dot product is not enough — valves has the biggest dot (15) yet the lowest cosine, because cosine divides out length. These are exactly the scores the pipeline showed: ranking by cosine is the whole of \(R_k\).

cosine-retrieval by-hand. Vectors from l10-rag.retrievalMath. dot = 10 / 11 / 15; ‖q‖ ≈ 3.873; ‖d‖ ≈ 3.1623 / 3.6056 / 5.4772. cos to 4 dp = 0.8165 / 0.7877 / 0.7071, which round to the 0.82 / 0.79 / 0.71 the pipeline displayed (recomputed from raw vectors, never hand-picked). Lesson: valves has the largest dot (15) but lowest cosine — length normalization matters.

The token budget

the context window caps max k
$$ k_{\max} = \left\lfloor \frac{4096 - 200 - 30 - 512}{256} \right\rfloor = \left\lfloor \frac{3354}{256} \right\rfloor = \mathbf{13} $$ $$ \text{at } k=4:\quad \text{stuffed} = 4\times 256 = 1024, \quad \text{prompt} = 200+30+1024 = 1254, \quad \text{headroom} = 4096-1254 = 2842 $$

Context window 4096; system 200 + query 30 + reserve 512. So \(k \le 13\): the window caps how much you can retrieve — which is exactly why ranking matters. Spend the budget on the best passages.

climb-rag token budget. kMax = floor(3354/256) = 13. Integers gated vs data/l10-rag.json; provenance_l10 pins kMax = floor((ctx-sys-q-reserve)/chunk).

Act 1 · How you cut

How you cut decides what you can find

You can only retrieve a whole chunk. If the answer is split across two chunks, no single retrieval brings it back whole. Chunk Norris chops the scroll; Tokenosaurus reminds us the pieces are sub-word tokens. The knobs: size and overlap.

turn-chunking. Chunk Norris + Tokenosaurus cameo. Chunking is the input stage that decides everything downstream.

Size, overlap, by hand

binary answer-containment · answer at [380,470]
$$ \text{chunks} = \left\lceil \frac{L - \text{overlap}}{\text{size} - \text{overlap}} \right\rceil $$ $$ \text{size}=200,\ \text{overlap}=0:\ \lceil 1000/200 \rceil = \mathbf{5},\quad \text{answer straddles boundary } 400 \;\Longrightarrow\; \text{recall@3} = \mathbf{0} $$ $$ \text{size}=200,\ \text{overlap}=50:\ \lceil 950/150 \rceil = \mathbf{7},\quad [300,500] \text{ holds } [380,470] \;\Longrightarrow\; \text{recall@3} = \mathbf{1.0} $$

Overlap costs storage and buys recall — the answer no longer falls between the cracks. Frontier: Late Chunking (Günther et al., 2024) embeds the whole document first, chunking after the transformer, so no overlap-vs-context tradeoff.

Four ways to cut

fixed · recursive · semantic · late — cost vs structure (representative)

Going down the table trades cheapness for structure-awareness. The first three cut before embedding, so each chunk is embedded in isolation; late-chunking inverts the order — embed first, cut later — which is the frontier idea on the next slide.

Frontier · Late Chunking

embed the whole document, then chunk
Frontier idea · arXiv:2409.04701
Encode the entire document first; cut into chunks after the transformer, before mean-pooling each chunk's token vectors.
  • ·Fixes: naïve chunking embeds each chunk alone → "it" / "the company" loses its referent.
  • ·Trick: attention saw the whole document, so every token vector is contextualized — pooling keeps it. No overlap-vs-context tradeoff.
  • ·Training-free: reuses any long-context embedder — just invert cut-then-embed (Günther et al., 2024).
  • ·Limit: the tradeoff vanishes only within the encoder's context window — a document longer than it must still be macro-split (the paper's "long late chunking" re-introduces a bounded overlap between macro-windows).
Late-Chunking frontier definition. arXiv:2409.04701 (Günther et al., Jina AI). Embed-then-chunk, training-free, fixes isolated-chunk context loss — the exact tension the sweep slide exposed (overlap buys recall but not context).
Act 1 · Index smarter

What you store decides what you can ask

Chunking is only the first cut. You can index the same document in several representations, or build a tree of summaries so one index answers both zoomed-out and zoomed-in questions. The index is a design choice, not a given.

divider-index-smarter. Bridges from chunking to richer indexing: multi-representation indexing + RAPTOR. Still Act 1 (the build-time half of the pipeline).

Multi-representation indexing

index a summary, retrieve the full chunk
Definition
Embed and index a derived representation of each document — a summary, a hypothetical question, a set of propositions — but return the full chunk to the generator.
  • ·Why: what reads best for retrieval (a tight summary that matches a query) is not what reads best for generation (the full passage with the details). So split them: index the summary, store a pointer to the raw chunk.
  • ·Examples: summary-indexing, "parent-document" retrieval (match a small chunk, return its larger parent), and hypothetical-question indexing.
  • ·Callback (L8): ColBERT is a related but distinct idea — a multi-vector index: many vectors of the same text, not (as here) indexing a derived view and returning the original. (We taught it in L8; here it's one of several.)
multi-representation-indexing definition. Index a derived view (summary / hypothetical question / proposition / parent-doc), return the full chunk. ColBERT is a ONE-LINE callback only (L8 owns it — do not re-teach MaxSim).

RAPTOR — a tree of recursive summaries

build bottom-up, retrieve at any level (←/→)

8 leaf chunks → 3 cluster summaries → 1 root, depth 3. Retrieval can pull from any level — the root answers a broad question, a leaf answers a detail. One index serves both zoom levels (Sarthi et al., ICLR 2024).

RAPTOR walkthrough (raptor-tree, l10-raptor). 8→3→1, depth 3 (integers → coverage-safe). Cite arXiv:2401.18059. Built bottom-up; retrieve at any level. NB: the 8→3 fan-in is a hard-partition TOY — the paper actually clusters SOFTLY via Gaussian mixture models over UMAP-reduced embeddings, so one chunk can feed several parent summaries (overlapping clusters). Retrieval default is the "collapsed tree": pool every node across all levels and retrieve by similarity (taught above as the flat all-levels index). Closes Act 1's indexing arc.
Act 2 · Aim the retriever

Hear the real question

The captain's words are rarely the corpus's words. Retrieval matches the words it's given — so translate the query before retrieving: expand it, rewrite it into answer-shape, fuse several phrasings, or break a compound question apart. Same retriever, a better query.

turn-query-translation. The aiming stage. No creature (plain metaphor). Clippy is reserved for L12 — do NOT use it. Act 2 covers vocabulary gap, multi-query, HyDE, RAG-Fusion, decomposition, step-back.

The vocabulary gap

why the right doc can rank low
Definition
A query and its true answer often use different words for the same idea — so a retriever scoring by word/embedding similarity ranks the right document below worse matches.
  • ·Example: "How does the heart pump blood?" vs a doc on "the cardiac cycle, ventricular systole" — same topic, almost no shared vocabulary.
  • ·Callback (L3): Furnas et al. found two people pick the same word for a concept under 20% of the time. Embeddings narrow the gap; they don't close it.
  • ·The move: don't build a better retriever — give it a better query, closer in vocabulary to the answer. That is query translation.
vocabulary-gap definition. The query and answer use different words → true doc ranks low. Callback L3 (Furnas et al., <20% agreement). Motivates query translation (the next moves: multi-query, HyDE, fusion, decomposition).

Multi-query

ask several ways, take the union
Definition
Have an LLM rewrite the query into several paraphrases, retrieve the top-k for each, and return the union of their results.
  • ·Why it works: each phrasing lands near a different part of the relevant set. One query might miss "ventricular systole"; another phrased around "diastole" catches it. The union covers more of the gold set — it lifts recall.
  • ·Cost: one LLM call to generate paraphrases, then several retrievals instead of one. The results are de-duplicated before they hit the generator's budget.
  • ·It widens coverage; the next move — HyDE — instead changes the shape of the query. They are complementary.
multi-query definition. Paraphrase → retrieve each → union → recall lift. Cost: 1 LLM call + several retrievals, de-duplicated. Contrast with HyDE (shape, not coverage). The by-hand lift (0.4→0.8) is two slides on.

Multi-query union recall, by hand

a separate 5-relevant gold-set
$$ \text{recall@5} = \frac{|\text{gold} \cap \text{found}|}{|\text{gold}|}, \qquad |\text{gold}| = 5 $$ $$ \text{single query: } 2/5 \Rightarrow \mathbf{0.4} \qquad \text{union of 3 paraphrases: } 4/5 \Rightarrow \mathbf{0.8} $$

The bare query finds 2 of the 5 relevant docs; three paraphrases together cover 4 of 5 — one phrasing still misses the last gold doc. The union lifts recall without touching the retriever — it just asks the same question several ways. The lift is diversity-dependent with fast diminishing returns, and the extra candidates compete for the token budget, so this 0.4→0.8 is a toy, not a guaranteed doubling. (This is its own gold-set, never blended with HyDE's single-true-doc count.)

multi-query union recall by-hand. l10-rewrite.multiQuery: single 2/5 = 0.4 → union 4/5 = 0.8 (both gated, anchored 2/5⇒0.4 and 4/5⇒0.8). Separate 5-relevant gold-set — never blended with HyDE's binary recall.

HyDE reciprocal rank, by hand

single true doc · RR = 1/rank
$$ \text{RR} = \frac{1}{\text{rank of the true doc}} $$ $$ \text{original: true doc rank } 8 \;\Longrightarrow\; \text{recall@5} = 0, \quad \text{RR} = 1/8 = \mathbf{0.125} $$ $$ \text{HyDE: rank } 2 \;\Longrightarrow\; \text{recall@5} = 1, \quad \text{RR} = 1/2 = \mathbf{0.5} $$

HyDE closes the vocabulary gap by searching with answer-shaped text; multi-query widens coverage by asking several ways. Both lift the ranking without touching the retriever — they just feed it a better query.

HyDE single-doc binary recall (RR 0.125→0.5, anchored 1/8=0.125 and 1/2=0.5). provenance_l10 pins RR=1/rank and the two recall senses on their own gold-sets.

HyDE, formally

embed a hypothetical answer, not the question
Definition · arXiv:2212.10496
Ask an LLM to write a hypothetical answer to the query, embed that document, and retrieve with its vector — even though the hypothetical may be partly wrong.
  • ·Why it works: an answer-shaped paragraph lives in the same region of embedding space as the real answers. Searching with it closes the vocabulary gap — the hypothetical's shape matters more than its factual accuracy.
  • ·Precise Zero-shot Dense Retrieval: Gao, Ma, Lin & Callan (ACL 2023) showed it lifts retrieval with no relevance labels — the LLM supplies the missing query-document bridge.
  • ·Cost & risk: one extra LLM call per query, and a confidently-wrong hypothetical can mislead retrieval — pair it with a retriever that still ranks the true doc highly.
  • ·When it fails: the lift assumes the LLM can place the answer in roughly the right topical region. For rare entities, fresh facts, or domains the model never saw, the hypothetical is topically off — not just factually wrong — and HyDE can rank the true doc lower than the bare query. Shape helps only when the model can guess the right neighbourhood.
HyDE-formally definition. Cite Gao, Ma, Lin & Callan, "Precise Zero-Shot Dense Retrieval without Relevance Labels", ACL 2023 (arXiv:2212.10496). Shape > accuracy; closes the vocabulary gap; costs one LLM call.

RAG-Fusion = multi-query + RRF

fuse the paraphrase rankings, not their scores
$$ \text{RRF}(d) \;=\; \sum_{\text{lists}} \frac{1}{k + \text{rank}_{\,d}}, \qquad k = 60 $$ $$ \text{multi-query gives several ranked lists} \;\longrightarrow\; \text{RRF fuses them into one order} $$

Callback (L3, L8): this is exactly Reciprocal Rank Fusion — the same \(\sum 1/(60+\text{rank})\) we used to fuse sparse + dense. RAG-Fusion reuses it across the paraphrases of one query: rank-based, no score calibration, and a doc that several phrasings agree on rises to the top.

RAG-Fusion = multi-query + RRF. REUSE the locked RRF Σ1/(60+r), k=60 — callback to L3 (fusion) and L8 (hybrid RRF). Do not re-derive RRF; it's owned earlier. Sets up the by-hand consensus on the next slide.

RAG-Fusion, by hand — consensus wins

two paraphrase lists · k=60
$$ \text{list A: } [\text{circulatory},\ \mathbf{cardiac\_cycle},\ \text{anatomy},\dots] \qquad \text{list B: } [\mathbf{cardiac\_cycle},\ \text{systole},\ \text{circulatory},\dots] $$ $$ \text{cardiac\_cycle (rank 2 in A, rank 1 in B): } \tfrac{1}{60+2}+\tfrac{1}{60+1} = \mathbf{0.0325} $$ $$ \text{circulatory (rank 1 in A, rank 3 in B): } \tfrac{1}{60+1}+\tfrac{1}{60+3} = \mathbf{0.0323} $$

Circulatory tops list A, yet loses the fusion: \(\mathbf{0.0325} > \mathbf{0.0323}\). The consensus doc — ranked highly by both paraphrases — beats the doc that one list alone loved. Agreement across phrasings is the signal RAG-Fusion rewards.

RAG-Fusion by-hand. l10-fusion: consensus doc_cardiac_cycle RRF 0.0325 beats list-A leader doc_circulatory 0.0323 (both gated/covered). The other six RRF scores stay in the data file (not displayed). Lesson: consensus beats a single high rank — the same as L8's hybrid RRF.

Decomposition & step-back — reshape the question

fan a compound query out · or abstract it up (←/→)

Decomposition: one compound question fans into two atomic sub-questions — recall per sub = [1, 1], but a single joint retrieval = 0. Step-back: abstract a too-specific question up to a generic one, retrieve the principle, then answer.

decomposition walkthrough (query-tree, l10-decomp). recallSub [1,1] vs recallJoint 0 (integers → safe). Steps 3–4 are the step-back ladder (cite arXiv:2310.06117) — the next slide names it formally.

Step-back, formally

climb to retrieve, descend to answer
Definition · arXiv:2310.06117
Abstract a too-specific question into a generic one, retrieve the underlying principle, then answer the specific question with it.
  • ·Trap: "Why did my heart rate hit 180 bpm running upstairs?" is so specific that no chunk states it — the literal query retrieves nothing.
  • ·Move: step back to "What regulates heart rate under exertion?" — which does match a chunk. Retrieve the principle, then reason down.
  • ·vs decomposition: decomposition fans out; step-back abstracts up. Both query translation — Zheng et al. (2023).
step-back definition. l10-decomp.stepBack; cite Zheng et al., "Take a Step Back", arXiv:2310.06117 (2023). Contrast: decomposition fans out, step-back abstracts up. Paired with the query-tree figure (steps 3–4) on the previous slide.

Act 3 · Routing & construction

Send the query where it belongs

One pipeline rarely fits every question. Some queries want a different data source, a different prompt, or a different query shape entirely. Routing picks the destination; construction turns the natural-language question into a structured retrieval.

divider-routing. Act 3: logical routing (pick a source), semantic routing (pick a prompt), and query construction (NL → metadata filter / SQL). The pipeline becomes a system, not a flat pipe.

Logical routing

let the LLM pick the data source
Definition
Give the LLM a menu of data sources (indices, tools) and have it classify which one the query belongs to — a function call over a constrained set.
  • ·Example: a code question routes to docs; billing to the SQL database; general to the web. One classifier, several back-ends.
  • ·How: structured output (an enum / function-calling schema), so the route is a valid label the system dispatches on — not free text.
  • ·vs semantic: logical reasons over an explicit menu; semantic (next) picks by embedding similarity — logical when choices are nameable.
logical-routing definition. LLM classifies the query into one of a named menu of sources/indices/tools (structured output / function call). Contrast with semantic routing (similarity-based). No gated numbers.

Semantic routing & query construction

route by cosine to a prompt centroid, then construct (←/→)

Embed the query, take cosine to each prompt-template centroid, route to the argmax (howTo wins). Then construct: the same question becomes a metadata filter (self-query) or an executable SQL query (text-to-SQL).

semantic-routing walkthrough (semantic-router, l10-routing). sims 0.8058 / 0.9670 / 0.6447 (in widget-data JSON → stripped by the coverage-guard, rendered by the widget) → route howTo. Steps 3 introduces construction (self-query + text-to-SQL), expanded on the next slides.

Query construction

natural language → a structured retrieval
Definition · text-to-metadata
Translate the natural-language query into a structured form the store can execute — a metadata filter, SQL, or graph query — instead of (or alongside) vector search.
  • ·Why: "papers on retrieval published after 2020" hides a hard constraint (year > 2020) that embeddings approximate poorly. A filter enforces it exactly; vector search ranks within it.
  • ·Two forms: self-query extracts a metadata filter (applied next to vector search); text-to-SQL compiles the question into a query over a structured store.
  • ·This is where unstructured retrieval meets the structured world — the LLM is the compiler from intent to query.
query-construction definition (text-to-metadata). NL → structured retrieval: metadata filter (self-query) or SQL (text-to-SQL). Hard constraints (year>2020) that embeddings approximate poorly become exact filters. The next slide shows both by example.

Act 4 · Make retrieval reliable

When one pass isn't enough

The recall floor still caps the answer. So spend more compute where it pays: re-rank the shortlist with a cross-encoder, grade the retrieval and self-correct (CRAG, self-RAG), and route by question complexity (adaptive-RAG). Then read the whole menu as one matrix.

divider-advanced-retrieval. Act 4: cross-encoder re-rank (callback L7), CRAG + self-RAG as control flow, adaptive-RAG as a complexity router, and the 7-strategy matrix centerpiece.

Cross-encoder re-rank — fix the order, cheaply

re-score the shortlist · callback L7 (the Judges) (←/→)
0/4
cross-encoder re-rank e2e (l10-rerank). Bi-encoder order d1 d3 d4 d2 d5 buries the only graded-relevant doc (d2, gain 3) at rank 4; the cross-encoder re-scores the SAME 5 → d2 d4 d1 d3 d5, lifting d2 to rank 1. nDCG@5 0.4935 → 1.0, MRR 0.3333 → 1.0 (exact before-values kept in notes — 0.4935/0.3333 are not in the coverage pool, so only the perfect 1.0 is shown on-slide). You pay the cross-encoder on k candidates only, not the whole corpus. But the cross-encoder is itself a fallible model — on hard pairs it can DEMOTE the right doc, and it adds k forward-pass latency; the gate is recall (it can only reorder what the bi-encoder surfaced) AND re-ranker quality. Callback L7 (the Judges).

Why the metric jumps — by hand

nDCG = DCG / IDCG · two graded docs: the answer (gain 3) and a partially-relevant doc (gain 1)
$$ \text{DCG} = \sum_i \frac{\text{gain}_i}{\log_2(i+1)}, \qquad \text{nDCG} = \frac{\text{DCG}}{\text{IDCG}} $$ $$ \text{before (gain-3 answer at rank 4): } \text{nDCG@5} = \frac{1/\log_2(4)+3/\log_2(5)}{3/\log_2(2)+1/\log_2(3)} \;<\; 0.5 $$ $$ \text{after (relevant doc at rank 1): } \text{nDCG@5} = \frac{\text{IDCG}}{\text{IDCG}} = \mathbf{1.0} $$

Discounted gain falls fast with rank, so burying the gain-3 doc at rank 4 wastes most of it (nDCG below half). Lift it to rank 1 and the order is ideal — nDCG@5 = 1.0. The cross-encoder didn't find a new doc; it just put the right one on top.

re-rank by-hand. nDCG = DCG/IDCG (callback L4). Before = 0.4935 (shown symbolically as <0.5 — the exact 0.4935 and MRR 0.3333 are not in the coverage pool, so kept in notes); after = 1.0 (ideal order, covered/anchored elsewhere). gains d2=3, d4=1 from l10-rerank.

Self-correcting RAG — grade, then act

CRAG branches on a retrieval grade · self-RAG self-critiques (←/→)

CRAG grades each retrieval correct / ambiguous / wrong and branches — use as-is, web-augment, or discard & rewrite. Self-RAG goes further: the model emits reflection tokens (Retrieve · IsRel · IsSup · IsUse) that gate retrieval and self-critique.

CRAG + self-RAG walkthrough (rag-control-flow, l10-selfrag). Steps 0–2 = CRAG (cite arXiv:2401.15884); steps 3–4 = self-RAG (cite arXiv:2310.11511). Thresholds 0.7/0.3 are single-decimal + in widget-data → coverage-safe. The next slide names self-RAG formally.

Self-RAG, formally

the model learns to decide when & whether to retrieve
Definition · arXiv:2310.11511
Train the LM to emit reflection tokens — Retrieve · IsRel · IsSup · IsUse — that gate retrieval and critique its own output as it generates.
  • ·Retrieve — decide per segment whether retrieval is needed at all (skip what the model already knows).
  • ·IsRel / IsSup — is the passage relevant, and each claim supported by it? The seed of faithfulness (metric in L11).
  • ·IsUse — is the response useful? CRAG bolts a grader on; self-RAG bakes critique in — Asai et al. (ICLR 2024).
self-RAG definition. Cite Asai et al., "Self-RAG", ICLR 2024 (arXiv:2310.11511). Reflection tokens Retrieve/IsRel/IsSup/IsUse. IsSup is the seed of faithfulness — defer the METRIC to L11. Contrast: CRAG bolts on, self-RAG bakes in.

Adaptive-RAG

match the effort to the question
Definition · arXiv:2403.14403
A lightweight complexity classifier routes each query to the cheapest strategy that can answer it: no retrieval · single-step RAG · multi-step (iterative) RAG.
  • ·Simple / known facts → answer directly, no retrieval (don't pay for what the model already knows).
  • ·Single-hop → one retrieve-then-generate pass — the classic loop.
  • ·Multi-hop / compositional → iterate (decompose, retrieve, reason, repeat). The router spends compute only where the question earns it — Jeong et al. (NAACL 2024).
adaptive-RAG definition. Cite Jeong et al., "Adaptive-RAG", NAACL 2024 (arXiv:2403.14403). Complexity classifier → no-retrieval / single-step / multi-step. The meta-lesson for the matrix + boundaries slide: match effort to question, don't over-engineer.

"More stages always help"

applicability boundaries — don't over-engineer
What students think

“Always add more retrieval techniques — if re-rank, CRAG and self-RAG each add quality, stacking all of them must be best.”

Every stage adds an LLM call, latency, and a new failure point — a grader can mis-grade, a re-ranker can re-bury. Cost compounds; quality saturates. Many techniques target the same failure: if your problem is phrasing, multi-query already fixes it — adding CRAG buys nothing but latency. Diagnose the failure mode first, then add the one stage whose lift matches it. Start naive; earn each stage with a measured win — which is exactly what adaptive-RAG automates.
applicability-boundaries misconception. Don't over-engineer: each stage costs latency + a failure point; many target the same failure. Diagnose first, add the one stage that matches, earn each stage. adaptive-RAG automates it. Pairs with the matrix.

Anatomy of a grounded prompt

system · context · question — answer using only the context
Definition · the generation prompt
The prompt that turns retrieved chunks into a grounded answer has three parts: a system instruction, the retrieved context, and the question.
  • ·System: "Answer using ONLY the context below. If it isn't there, say you don't know. Cite every claim." — the instruction that forces grounding.
  • ·Context: the reranked top-k chunks, each tagged with its source id — what fits the token budget (recall \(k_{\max}\)).
  • ·Question: the user's query. "Use only the context" + "cite sources" make the answer citeable and auditable — the cure for the bare-LLM failures.
generation-prompt-anatomy definition. system + context + question. The "answer using ONLY the context" and "cite sources" clauses force grounding/citeability — the cure for the three bare-LLM failures (stale/unciteable/confident). Ties back to the anchor trace's prompt.

Faithfulness vs relevance

two different questions about one answer (→ L11)
Definition · the two axes of a RAG answer
Faithfulness: is every claim in the answer supported by the retrieved context?  ·  Relevance: does the answer actually address the question?
  • ·They are independent. An answer can be faithful but irrelevant (true to the context, but off-topic) or relevant but unfaithful (on-topic, but invents facts the context never stated).
  • ·Self-RAG's IsSup token is a faithfulness check; its IsUse token is closer to relevance — the system already distinguishes these two axes.
  • ·The catch: a confident answer can be high on one axis and zero on the other — and look identical from the outside. How to measure each is the whole of L11 — we only name the axes here.
faithfulness-vs-relevance definition. Two independent axes: faithfulness (supported by context) vs relevance (answers the question). DEFER the metric to L11 — only name the axes here (course boundary: faithfulness METRICS owned by L11). Connects to self-RAG's IsSup/IsUse.

Garbage in, fluent garbage out

Confabulous, the hallucination phantom (first appearance)
What students think

“Fluent output means the answer is correct — if the model writes a confident, well-formed reply, the system worked.”

If retrieve brings back wrong passages, augment stuffs them in, and generate dutifully writes a fluent, confident answer grounded in garbage. The recall floor strikes again: the generator can only be as good as what retrieval brought back. Everything in this lecture — chunking, query translation, routing, re-rank, self-correction — exists to keep garbage out of that context. Confabulous hands the Oracle a forged citation, and it recites it with the same assurance as a true one.

Confident and correct look identical from the outside — which is precisely the problem the next lecture must solve. How do you grade an Oracle?
