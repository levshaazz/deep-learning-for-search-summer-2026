Пять строк из шести совпадают. Каждый ассерт формы проходит, ничего не падает, стектрейса не будет никогда. В коде ось нормировки — одно целое число, которое не проверяет ни один линтер. Единственное во всём конвейере, что записывает, по какой оси нормировали, — ориентация треугольника. Five rows out of six are identical. Every shape assertion passes, nothing crashes, no stack trace ever appears. In the code the axis is one integer that no linter checks. The only thing in the entire pipeline that records which axis was normalised is the orientation of the triangle.

Разбираем баг 2 медленно и по одной улике. Внимание нормирует строку скоров: для каждого запроса — распределение по ключам, строки суммируются в единицу. Перепутайте ось — и в единицу начнут суммироваться столбцы: каждый КЛЮЧ раздаёт свою единицу массы по запросам. Модель по-прежнему что-то считает, но это уже не внимание: запрос больше не выбирает, на что смотреть, — он конкурирует с другими запросами за право быть замеченным ключом. Теперь по таблице. Форма на входе n на n, на выходе n на n — совпадает. Строка einsum: softmax не съедает ни одной буквы, слева nm, справа nm — совпадает, и это принципиально: einsum записывает, какие оси УМИРАЮТ, а не какие нормируются. Формула — та же сигма, ось нормировки в неё просто не входит, она живёт в словах вокруг формулы. Код — единственное место, где ось вообще упомянута: dim=-1 против dim=-2. Один символ. Ни один тайп-чекер, ни один shape-ассерт, ни один линтер этого не проверяет, потому что проверять нечего: формы совпадают. Остаётся схема. NCD рисует треугольник ПОПЕРЁК той оси, по которой нормирует, — и повёрнутый треугольник виден с другого конца комнаты. Это и есть ответ на вопрос «зачем нам ещё одна нотация»: она делает видимым ровно то, что не видит ни один инструмент в стеке. Числовых величин на слайде нет — только формы (n×n) и имена осей.
