«Late chunking встроен в X» чаще всего означает «в блоге X есть рецепт». Проверяй по документации, а не по посту. “Late chunking is built into X” usually means “X’s blog has a recipe”. Check the docs, not the post.

Ловушка · 8192 на весь массив The trap · 8192 for the whole array

С флагом late_chunking=true лимит в 8192 токена начинает считаться на весь массив input, а не на каждую строку. Иначе и быть не может: чтобы усреднять поздно, сервис склеивает вход в один текст и прогоняет его одним проходом.With late_chunking=true the 8192-token limit applies to the whole input array, not per string. It cannot be otherwise: to pool late the service concatenates your input into one text and runs a single pass.

Отсюда два следствия, которые ломают наивную миграцию: батч, который вчера проходил, сегодня отваливается по лимиту; и порядок строк в массиве становится значимым — соседние чанки теперь влияют друг на друга.Two consequences break a naive migration: a batch that passed yesterday now trips the limit; and the order of the strings starts to matter — neighbouring chunks now influence one another.

Не клади в один запрос чанки из разных документов — иначе внимание честно свяжет их между собой.Never put chunks from different documents in one call — attention will dutifully bind them together.

The practical availability slide. Jina's API has late_chunking=true as a flag; Chonkie ships a LateChunker (SentenceTransformer models only); Weaviate / Elasticsearch / Qdrant have blog recipes, NOT native support — say that plainly, the folklore says otherwise. One-vector APIs cannot do it at all. The trap is the one that costs real time: with the flag on, the 8192-token budget applies to the WHOLE input array rather than per string, because the service concatenates the array into one text to pool late. Hence batches that used to fit now fail, the order of the array becomes semantically meaningful, and mixing chunks from different documents into one call makes attention bind unrelated documents together.
