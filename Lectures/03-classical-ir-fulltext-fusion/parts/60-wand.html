WAND: почему мы не оцениваем каждое вхождениеWAND: why we don't score every posting

top-\(k\) с верхними границами счёта with score upper bounds

ИдеяThe idea

У каждого терма есть верхняя граница max-score. Держим текущий порог = \(k\)-й лучший счёт на данный момент. Пропускаем любой документ, чья лучшая возможная сумма не может побить порог.Each term has a max-score upper bound. Keep a running threshold = the \(k\)-th best score so far. Skip any document whose best possible sum can't beat the threshold.

i
BlockMax-WAND

Хранит max-score на каждый блок вхождений, поэтому целые блоки пропускаются. Сублинейный top-\(k\) на практике.Stores max-scores per block of postings, so whole blocks are skipped. Sublinear top-\(k\) in practice.

Почему это важноWhy it matters

  • ·Нам нужен лишь top We only need the top \(k\) (напр. 1000), а не каждый счёт. (e.g. 1000), not every score.
  • ·Большинство документов не достигают порога → никогда не оцениваются полностью.Most documents can't reach the threshold → never fully scored.
  • ·Замыкает круг с Частью 1: именно так BM25 укладывается в бюджет задержки в веб-масштабе.Closes the loop with Part 1: this is how BM25 hits the latency budget at web scale.
The bridge back to the latency budget. We claimed the index lets us avoid scoring most documents; WAND is the algorithm that delivers it for ranked retrieval. Each term knows the maximum contribution it can ever make, so the algorithm maintains a threshold equal to the current k-th best score and refuses to fully evaluate any document whose optimistic upper-bound sum cannot beat that threshold. BlockMax-WAND tightens this with per-block maxima, skipping whole runs of postings. The result is that top-k retrieval is effectively sublinear, which is exactly why BM25 over an inverted index meets a hundred-millisecond budget on billions of documents.
