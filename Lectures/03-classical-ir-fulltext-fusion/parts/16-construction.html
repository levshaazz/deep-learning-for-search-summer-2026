ПроблемаThe problem

Полный список пар терм–документ не помещается в RAM. Оба классических алгоритма строят блоки в памяти, затем сливают на диске.The full term–doc pair list doesn't fit in RAM. Both classic algorithms build blocks in memory, then merge on disk.

  • ·BSBI (блочная сортировка): собираем пары (blocked sort-based): collect (termID, docID), сортируем каждый блок, пишем на диск, затем внешнее слияние. pairs, sort each block, write to disk, then external-merge.
  • ·SPIMI (однопроходный в памяти): наращиваем вхождения по каждому терму напрямую, без глобальной сортировки; сбрасываем блок, когда память заполняется. (single-pass in-memory): grow per-term postings directly, no global sort; flush a block when memory fills.

Сегменты LuceneLucene segments

Новые документы образуют маленькие неизменяемые сегменты; фоновые слияния объединяют их в более крупные. Записи только добавляются; удаления — это надгробия (tombstones).New documents form small immutable segments; background merges combine them into larger ones. Writes are append-only; deletes are tombstones.

Именно так Elasticsearch / Solr индексируют непрерывно, не перестраивая весь индекс.This is how Elasticsearch / Solr index continuously without rebuilding the whole index.

Construction must be out-of-core because the pair list dwarfs RAM. BSBI sorts blocks of termID-docID pairs and external-merges them; SPIMI skips the global sort by accumulating postings per term and flushing when memory runs out — simpler and faster in practice. Real engines layer on segments: every flush is an immutable segment, and a background merge policy keeps the segment count bounded, which is what makes near-real-time indexing possible.
