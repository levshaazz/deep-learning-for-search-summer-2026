The cascade as a table

Stage 0 / 1 / 2 — job, cost, set size
Stage Job · model Cost / doc Set size Optimises
Stage 0 · retrieval candidate-gen · BM25 / ANN very cheap \(\sim 10^{9} \to 10^{3}\) recall
Stage 1 · ranking GBDT / LTR, many features moderate \(\sim 10^{3} \to 10^{2}\) order quality
Stage 2 · re-rank cross-encoder + rules expensive \(\sim 10^{2} \to 10\) precision@k

YouTube (Covington 2016): candidate-gen millions → hundreds, then a compact dense ranking tower over large embedding tables, serving in tens of ms. MS MARCO: a BERT cross-encoder lifted MRR 16.7 → 36.5, but only feasible on a ~100-doc shortlist.

Concrete numbers anchor the abstraction. YouTube's two-stage system (Covington et al., RecSys 2016) is the canonical example — candidate generation shrinks millions to hundreds, then a compact dense ranking tower (a few fully-connected ReLU layers over large sparse embedding tables) scores the survivors, all under tens of milliseconds. MS MARCO shows the precision payoff of Stage 2 (re-rank): Nogueira & Cho's BERT re-ranker more than doubled MRR, but attention is quadratic, so it is only affordable on the shortlist the cascade hands it.
