Case study: measured pain → engineered fix

371M docs · 2 languages · 1s SLA

Before (naive)

Embed all 371M docs with a multilingual model, float64, dimension 768.

!
Resource ledger

Vector store shape \((371\text{M}, 768)\) — huge memory; no GPU available for inference; brute-force similarity blows the 1s SLA.

After (engineered)

Cascade + ANN index, shrink embeddings to dimension 24, cache hot queries.

i
Resource ledger

Vector store shape \((371\text{M}, 24)\) — memory (no problem); ANN avoids brute force (no problem); top-100 in well under 1s (no problem).

Nearly the same retrieval quality (a small recall trade for the smaller embedding), at a tiny fraction of the resources. Every technique — cascade, smaller embeddings, caching — entered as the fix to a measured pain point, not as a default.

Ported from the old Lecture 1 PCA arc: a real task — 371M short multilingual strings, top-100 matches with a score, 1-second SLA. The naive ledger (768-dim float64 over 371M rows, no GPU) is unservable. The engineered ledger shrinks dimension 768 → 24 (e.g. via PCA / a smaller model), adds an ANN index and a cache, and every pain annotation flips to "(no problem)". The pedagogical pattern to reuse all term: introduce each technique as the answer to a measured bottleneck, never as a hammer looking for a nail.
