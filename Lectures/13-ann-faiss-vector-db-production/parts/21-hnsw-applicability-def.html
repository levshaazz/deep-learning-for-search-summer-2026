где N = число проиндексированных векторов, M = число рёбер графа, которые хранятся при каждом узле.where N = the number of indexed vectors, M = the number of graph edges kept per node.

Берись за него, когда: нужна наименьшая задержка запроса при высокой полноте, индекс помещается в RAM, а вставки приходят инкрементально (без пакетного переобучения). Поиск \(O(\log N)\), полнота настраивается вживую через efSearch.Reach for it when: you need the lowest query latency at high recall, the index fits in RAM, and inserts arrive incrementally (no batch retrain). \(O(\log N)\) search, recall tuned live via efSearch.

Издержки: высокое время построения, а память \(=\) сырые векторы плюс граф (\(\approx M\) рёбер на узел) — он хранит всё без сжатия.The costs: high build time, and memory \(=\) the raw vectors plus the graph (\(\approx M\) edges per node) — it stores everything uncompressed.

Поэтому HNSW в одиночку прожорлив по RAM на миллиарде векторов. Именно поэтому в продакшне его сочетают с PQ (HNSW-PQ) — граф ради скорости, коды ради памяти. Следующие коридоры, IVF и PQ, атакуют стену памяти напрямую.So HNSW alone is RAM-hungry at a billion vectors. That is exactly why production pairs it with PQ (HNSW-PQ) — the graph for speed, the codes for memory. The next lanes, IVF and PQ, attack the memory wall directly.

HNSW applicability def-card. Use when: lowest latency at high recall, fits RAM, incremental inserts. Costs: high build, memory = vectors + graph overhead (no compression). The billion-scale catch motivates IVF (partition) and PQ (compression), and HNSW-PQ as the combined production index. Bridges to the IVF lane.
